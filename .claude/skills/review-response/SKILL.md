# /review-response — レビュー対応の司令塔

PRレビューへの対応を**標準化・再現化**する。これは**司令塔**であり、既存の `/canon-check`・`/adr-new`・4レビュア（ui-terms / canon-schema / tests / correctness）の**責務は一切変えない**。必要に応じてそれらを**呼ぶだけ**。

## 入力
- 貼り付けられたレビュー結果、または PR番号。PR番号なら未解決コメントを取得：
  ```
  gh pr view <n> --comments
  gh api repos/:owner/:repo/pulls/<n>/comments   # 行コメントが要るとき
  ```

## 手順

### 1. 仕分け（要件1）
各指摘を重大度で分類：**🔴 ブロッカー／🟡 直すべき／ℹ️ 軽微・要確認**（リポジトリ慣習）。指摘ごとに「対応する／保留・押し返す」の方針を決める。

### 2. 妥当性判定（要件3）— **鵜呑みにしない**
各指摘を**正典に照合**する：`CLAUDE.md`（§条項）／`docs/yuko_recruit_docs/adr/*`／`schemas/*.schema.json`／`11`/`12`/`15` ほか設計資料。
- **正しい指摘** → 「修正対象」へ。
- **誤り or 正典と矛盾する指摘** → **押し返す**。該当する**条項・ADR番号・schema 箇所を引用**して根拠を示す（CLAUDE.md §9-3 正典>例示・§0 優先順位）。レビュアが上位ではない。
- 確証が持てないものは ℹ️＋「要確認」とし、断定しない。

### 3. 最小差分で修正（要件2・要件4）
- 指摘の**範囲だけ**を直す。**ついで修正・大規模リファクタ・スコープ外の変更は禁止**（CLAUDE.md §8 小さく動く単位／§9-5）。
- 作業中に気づいた別件は、ここで直さず **別タスク化（タスク管理ツール）か別PR提案**に留める（特定のツール名に依存しない書き方にする）。
- UI文言を触るなら §2-3/§2-5、enum/定数なら §2-7/§6 を自分でも踏む（正典違反の修正で新たな正典違反を作らない）。

### 4. 必要なら確認を振る（要件5）
修正が**正典に触れる**なら、確認を委譲する（責務は変えず呼ぶだけ）：
- 差分全体の整合 → `/canon-check`
- 観点を絞るなら個別に → `ui-terms-reviewer`（表示文言）／`canon-schema-reviewer`（enum・schema・依存方向）／`tests-reviewer`（§7テスト）／`correctness-reviewer`（不変条件）

### 5. 検証（要件6）
変更内容に応じて実行し、緑を確認：
- フロント：`npm run check:frontend`（lint→typecheck→test→validate:schemas）／必要に応じ `npm run test`・`npm run validate:schemas`
- Rust：**`npm run check:rust`（check→fmt→clippy）＋ `npm run check:rust:test`**（⚠️ fmt/clippy を省かない＝CI の `Rust (check/fmt/clippy)` と同じ3つ）
- UI挙動が変わるなら preview で動作確認（screenshot はこの環境でハングするため eval/snapshot でDOM確認）

### 6. コミット（要件7）
**検証が緑になってから**、リポジトリ規約でコミット：
```
fix(review): PR#NN レビュー対応（指摘の要約）

- [🔴/🟡/ℹ️] 指摘 → 対応内容（または押し返しの根拠）
...

Co-Authored-By: {{実行モデル名}} <noreply@anthropic.com>
```
※ `{{実行モデル名}}` は**実行時のセッションモデル名**に置き換える（例: `Claude Opus 4.8`／`Claude Sonnet 4.6`）。固定のモデル名をハードコードしない（帰属が不正確になるため）。スコープ外の変更は混ぜない。push して PR を更新。

### 7. レビュー返信案（要件8）
各指摘に1対1で対応づけた返信案を作る（@claude へのメンション返信や PR コメント用）：
- 対応済み（コミットSHA／変更点）／押し返し（根拠の条項・ADR・schema）／保留（理由・別タスク化）。

## 出力形式（必ずこの5節で返す）
```
## /review-response（PR#NN）
### 1. レビュー対応方針
（各指摘の 🔴/🟡/ℹ️ と「対応/保留・押し返し」の一覧）

### 2. 修正対象
（直す指摘と、最小差分の内容）

### 3. 保留・押し返し
（直さない指摘と、正典を根拠にした理由）

### 4. 実施結果
（verify/test の結果・コミットSHA・push 状況）

### 5. レビュー返信案
（レビュアへ返す文面）
```

## 原則
- **正典 > レビュア指摘。** 誤指摘は正典根拠で押し返す。直す前に必ず妥当性判定（手順2）。
- **最小差分・スコープ厳守。** ついで修正・大規模リファクタはしない（別タスク化）。
- **既存スキル/レビュアの責務は変更しない。** 本スキルは司令塔として呼ぶだけ。
- **緑にしてからコミット。** 検証を飛ばさない（DoD ①）。
