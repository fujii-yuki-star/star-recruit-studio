# /issue-drive — Issue を1本道で処理する

`/canon-check`（差分の検査）と `/review-response`（指摘への対応）の**間**にある、
「Issue を受け取ってから PR がレビューを通るまで」を標準化する。既存スキルの責務は変えず、**呼ぶだけ**。

## 引数

- Issue 番号（複数可）。省略時は「実施順の Issue（EPIC の表）から未着手のもの」を尋ねる。

## いちばん大事な前提

⚠️ **Issue に書いてあることを、そのまま信じない。**
このリポジトリの UI/UX レビュー由来の Issue は本文に **「⚠️ 未検証（レビュアの読解＝着手時に裏を取る）」** と
書いてある。実際、これまでに**レビュアの読解が実装と食い違った**ことが何度もあり、逆に
**レビューが挙げた4か所の外に5か所目があった**こともある（#990）。

**指摘を直す前に、指摘が成り立つことを自分で確かめる。** 確かめ方は3つ：

1. **コードを読む**（file:line を実際に開く。孫引きしない）
2. **走らせて見る**（小さな probe テストを書き、`console.log` で実測する。終わったら消す）
3. **確かめられないと分かったら、そう書く**（例＝jsdom は「要素が外れるときの `blur`」を出さないので
   その経路は判定できない）。⚠️ **確かめられない不具合に機械を足さない**＝その機械自体が次の種になる。
   **実機での確認手順つきで別 Issue にする。**

## 手順

### 1. 読む・裏を取る

- `gh issue view <n> --json body --jq '.body'`
- 指摘を**箇条に割る**（1件の Issue に3〜7件入っていることが多い）。
- 各件を上の3つのどれかで確かめ、**成立／不成立／確かめられない**に分ける。
- 不成立は**直さない**。理由（file:line と正典の条項）を PR 本文に書く。

### 2. 直す

- **写して増やさない**＝同じ規則が2か所以上に出てきたら、**関数を1つ作ってそこへ寄せる**
  （このリポジトリの不具合の多くは「双子の片方だけ直す」型）。
- 直した規則が**画面のあちこちに書き写される形**なら、**走査（scan テスト）を足す**。
  ⚠️ 走査は「歩くだけ」にしない＝**拾い方を純粋関数に切り出して直接叩く**
  （歩く形だけだと、拾い方を消しても「いまのコードに漏れが無いので緑」になる）。
- ⚠️ **静的な走査で表せない規則は、走査にしない**＝誤検出は門番の信用を落とす。
  描いて確かめる（既存の物差しを共有する）ほうへ倒す。

### 2.5. 「直した」と書いた行に、**差分の場所を並べる**

⚠️ **これは実際に2回踏んだ**（PR #1022・#1027）＝置換がどこにも一致せず落ちた／
5か所のうち2か所しか直していない、のに **PR 本文と正典だけが「直した」と言っている**状態で出した。
どちらもレビューが拾わなければ、そのまま「文書だけ直っている」機能として残っていた。

⚠️ **「自分で確かめる」では防げない**＝それは**注意力頼み**で、この土台が
「構造で防ぐ」と言って否定しているのと同じ種類の対策（PR #1018 レビューの指摘）。

**照合できる形にする：**

1. PR 本文と正典で「直した」「揃えた」「通した」と**書いた行ごとに**、対応する
   **`file:line`**（`git diff` のハンク）を挙げる。挙げられない行は**書かない**。
2. 「1か所へ寄せた」と書いたら、**呼び出し側の数を数えて出す**（`grep -c`）。
   *N か所すべてが通っている* を数で示す（「寄せた」だけでは、片方が残っていても書ける）。
3. 変えた文言は、**その文言で検索して**出た件数を出す。**画面まるごとで見る検査**を書く
   （文言ごとに書き並べる検査は、直し漏れた1か所を**構造的に**見つけられない＝#1027）。

⚠️ **編集が当たったことも同じ**＝置換したら**その場で `grep`** して件数まで見る。
`npm run mutate` は「当たらなければ止まる」を持っているが、**実装の編集そのものには無い**。

### 3. 検査を書き、**必ず変異チェックする**

```bash
npm run mutate <spec.json>
```

spec の雛形は `node scripts/mutate.mjs --print-template`。実行係が次を**構造で**担保する：

- ベースラインが緑でなければ**1つも変異させずに止まる**
- 書き換え先が**ちょうど1か所**に当たらなければ止まる（0か所＝無傷のまま緑＝いちばん質の悪い嘘）
- 正常・失敗・**中断**のどれでも書き換えたファイルを戻す

⚠️ **生き残った変異は「検査していない振る舞い」**。検査を足すか、**等価である理由**を書く。
⚠️ **自分がコメントに書いた主張も変異にする**（「1つでも通らなければ全体を変えない」等）＝
実際に、書いたのに検査していなかったことが何度もある。

### 4. 正典を同じ PR で直す

変更した規則の置き場所（`06`＝画面 / `11`＝データと関数 / `15 §6`＝エラーと状態 / `adr/`＝決定）。
⚠️ **実装だけ直して正典が古いまま**が繰り返し起きている（次に読む人は正典を信じる）。
⚠️ **コメント・正典の主張が実装より強くなっていないか**＝段2.5 の形（差分の場所を並べる）で照合する。

### 5. 通す

```bash
npm run check:frontend   # ⚠️ パイプで潰さない（`| tail` は終了コードを 0 にする）
```
Rust に触れたら `npm run check:rust` と `npm run check:rust:test` も。
正典に触れたら `/canon-check` を呼ぶ。

### 6. PR を出し、レビューを頼む

- 積み上げ（stacked）なら `--base` に親ブランチを指定し、**マージ順を本文の先頭に書く**。
- PR 本文に必ず入れる：**裏取りの結果**（成立／不成立とその根拠）／**変異チェックの一覧**／
  **未検証（実機でお願いしたいこと）**／**正典のどこを直したか**。
- `@claude` へのレビュー依頼は**コメント**で出す（`--body-file` を使う＝`--body` の中の
  バッククォートはシェルに食われる）。**静的読解のみ**をお願いし、実行結果は本文に書く。
- **迷った設計判断を名指しで聞く**＝いちばん有効な指摘はここから出る。

### 7. レビュー対応

`/review-response` を呼ぶ。⚠️ **鵜呑みにしない／根拠があれば押し返す**は同スキルのとおり。
⚠️ 指摘が正しかったときは、**自分がなぜ見落としたか**を1行残す（同じ型が次also来る）。

### 8. 締め

- Issue には**結末**（何を直し、何を別 Issue にし、何を実機に送ったか）を書いてから閉じる。
- 途中で見つけた別件は**その場で起票**する（直さない）。

## 原則

- **裏取りが先、修正は後。** 未検証の指摘をそのまま直さない。
- **1件ずつ最後まで。** 複数の Issue を同時に開かない（差分が混ざるとレビューが読めない）。
- **マージはしない。** PR を出してレビューが通るところまで。マージは利用者。
- **直せないものは、直せないと書く。** 確かめられない・判断が要るものは Issue にして送る。
