# /adr-new — ADR を起票する

大きな設計判断は**コードを書く前に** ADR に残す（CLAUDE.md §8）。このスキルは雛形作成と**索引・正典の同期**まで一気に行う。

## 手順

### 1. 入力の確認
- 引数からタイトル（決定の主題）を受け取る。曖昧なら一文の決定内容と状態（既定 **Proposed**）をユーザーに確認。勝手に決め切らない（§9-2）。
- 英語 kebab-case のスラッグを決める（既存例：`rendering-parity`/`ffmpeg-codec`/`aspect-ratio-and-portrait`）。

### 2. 採番と日付
```
ls docs/yuko_recruit_docs/adr/ | grep -oE '^[0-9]{4}' | sort -n | tail -1   # 最大番号
date +%F                                                                     # 本日(YYYY-MM-DD)
```
次番号は「最大＋1」を4桁ゼロ詰め。日付は本日の実値を使う（推測しない）。

### 3. 雛形作成 `docs/yuko_recruit_docs/adr/NNNN-<slug>.md`
`0000-template.md` を土台に、本リポジトリの実運用セクションで作る：
```markdown
# ADR-NNNN: タイトル

- **状態**: Proposed   ← 既定。確定済みなら Accepted
- **日付**: YYYY-MM-DD
- **関連**: 関連する正典/資料/先行ADR（例: `CLAUDE.md §x` / `11_SCHEMA_REFERENCE` / `schemas/*.json` / `ADR-000x`）

## コンテキスト
何を決めるのか。背景・制約・なぜ今決めるか。正典の現状（該当条項・行）を引く。

## 判断軸
優先する評価基準（テンプレ駆動の維持 §2-4／正典の単一参照 §2-7／非技術者UX §2-3 など、該当するもの）。

## 検討した選択肢
| 選択肢 | 評価 |
|---|---|
| (A) … | 利点/欠点・採用可否 |
| (B) … | … |

## 決定
採用する選択肢と理由。Proposed の場合は「決定（Proposed）」とし確定でないことを明示。

## 結果・影響
コード・他資料・将来への影響。**正典(schemas/11/12/CLAUDE.md)を変えるなら、その更新計画と schemaVersion／マイグレーション方針(§5)も書く。**

## 未解決の論点
後続で検証・決定すべきこと（ユーザー確認が要る点は「（ユーザー確認）」と明記）。
```

### 4. 索引と正典の同期（**必須・忘れない**）
1. **`docs/yuko_recruit_docs/adr/README.md`** の「一覧」テーブルに**新規行を追加**（`| [NNNN](NNNN-slug.md) | タイトル | **状態** |`）。これがこのスキルの主目的（索引ドリフト防止）。既存行は**作業中に状態のズレに気づいたら指摘する**程度にとどめ、全件の突き合わせ監査までは課さない（定期的な全件監査は /canon-check や別途の監査スキルで）。
2. **`CLAUDE.md §11`** に1行追記：Accepted は「決定済み（ADR）」、Proposed は該当箇所に「Proposed」と明記して載せる。MVP除外/将来対応に関わるなら §10 の注記も整合させる。
3. 関連する正典（`05`/`11`/`12`/`schemas` 等）に追従改訂が要るなら、ADR の「結果・影響」に列挙し、別コミットで反映する旨を書く（このスキルでは ADR＋索引＋§11 までを作る）。

### 5. 仕上げ
- 作成/更新したファイル一覧と、次にやること（関連正典の追従、レビュー）を提示。
- コミットは Conventional Commits（`docs:`）。状態が Proposed なら「承認後に実装」と明記。

## 原則
- **コメント・本文は日本語、識別子・スラッグは英語**（§6）。
- **推測でフィールド/enumを増やさない**（§9-2）。決め切れない点は「未解決の論点」へ。
- **索引と §11 の更新を省略しない** — ここを飛ばすと正典ドリフトになる（このスキルの存在理由）。
