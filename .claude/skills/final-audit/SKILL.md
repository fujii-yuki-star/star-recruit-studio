# /final-audit — 機能・リリース単位の出口監査

積み上がった**全体**を多観点で監査する（PR 単位では正しくても合成すると割れる挙動・ドリフト・観点の抜けを拾う）。`/canon-check` の姉妹スキル＝**差分ベースではなくスコープベース**。厳しさは**指摘の数ではなく敵対的検証の生存率**で担保する。

## 引数

- **凍結点**（省略時 HEAD）：監査対象コミット。作業ツリーに未コミット差分があれば**先に告げて確認**（走りながら監査しない）。
- **観点ファイル**（省略時は `docs/yuko_recruit_docs/audits/` の該当リリースのもの。無ければその旨を告げて基本観点のみで実行）：例 `docs/yuko_recruit_docs/audits/alpha5-timeline-final-audit-points.md`。
- `--skip-mechanical`：機械層を省略（既に緑と分かっているとき）。

## 手順

### 1. 凍結点の確定と記録

- 凍結点コミットの SHA を記録（レポートの行番号参照の基準になる）。
- 観点ファイルを読み、**「監査直前に最新化してから凍結」の但し書きが守られているか**（最終更新が直近か）を確認。古そうなら先に指摘する。

### 2. 機械層

- `npm run check:frontend`（lint→typecheck→test→validate:schemas）。Rust 対象なら `npm run check:rust` も。
- **赤があれば監査を始めない**（最優先の🔴として報告して終了。壊れたコードの監査は無駄撃ち）。

### 3. 入力の組み立て（コンテキスト制御＝このスキルの中心責務）

**エージェントに探索させない。渡すものは司令塔が組み立てる**：

- 観点ファイルを観点別の節に分解する。
- 観点ごとに**対象ファイル一覧**を作る（観点ファイルの指す領域を Glob/Grep で実ファイルに解決。リポジトリ全域を渡さない）。
- 各エージェントへの入力＝**①凍結点 ②対象ファイル一覧 ③観点ファイルの該当節（本文貼り付け） ④「担当外は申し送り1行・範囲外を読まない・出力形式厳守」の念押し**。この4点**だけ**。research 資料や正典の全文は渡さない（エージェント定義に焼き込み済みの物差しと、節に書かれた参照先で足りる）。

### 4. 観点別の並列監査

**1メッセージ内で全観点の Agent を同時起動**（互いに独立＝他観点の指摘を見せない）：

| subagent_type | 担当 |
|---|---|
| `canon-schema-reviewer` | 正典/schema 整合・直書き・依存方向 ＋（観点ファイルの指定があれば）機能スコープの docs ドリフト |
| `correctness-reviewer` | 不変条件・データフロー・V22〜V30 |
| `tests-reviewer` | §7 テスト網羅・golden・**新規テストの変異チェック実施記録** |
| `ui-terms-reviewer` | §2-3 技術用語・§2-5 文言 |
| `ux-model-reviewer` | 操作モデル＝業界の型との差分（利用者が気づけない違和感の検出） |
| `parity-reviewer` | preview=export の正準関数共有 |
| `error-state-reviewer` | エラーの到達可能性・silent fallback・後始末 |
| `resilience-reviewer` | 履歴・保存・並行ガード・資源・取り込み安全 |

観点ファイルに該当節が無い観点は省略してよい（省略したら明記）。

### 5. 敵対的検証（生存率で選別）

- 🔴・🟡 の各指摘を、**指摘した本人と別の**エージェント（`general-purpose`）へ1指摘=1エージェントで並列に渡す：「この指摘を**反証**せよ。file:line を実際に読み、指摘が成立しない根拠を探せ。反証できなければ CONFIRMED、できたら REFUTED と根拠」。
- REFUTED は捨てる（レポートの「押し返し記録」に根拠つきで残す）。ℹ️ は検証を省略してよい。
- 指摘ゼロの観点はそのまま「指摘なし」。**水増しさせない**（指摘が無いことは失敗ではない）。

### 6. プレビュー駆動チェック（司令塔自身が行う）

- 観点ファイルで**[プ]**（プレビュー駆動）の印が付いた項目は、エージェントではなく**司令塔がアプリのプレビューで確認**する（`.claude/launch.json` の dev サーバ）。実行できない環境なら**[実]（実機送り）へ降格**して明記する。

### 7. レポート保存

`docs/yuko_recruit_docs/audits/<YYYY-MM>-<scope>-final-audit-report.md` に保存：

```
# 出口監査レポート：<scope>
- 凍結点: <SHA> / 観点ファイル: <path>（最終更新 <date>）/ 実施日
- 機械層: 緑（または赤で中断）
## 判定表（観点×判定）
| 観点 | 判定 | 🔴 | 🟡 | ℹ️ |
## 指摘（検証済みのみ・重大度順）
- [🔴] path:line — 観点 — 内容 — 修正の方向（CONFIRMED by <検証>）
## 押し返し記録（REFUTED になった指摘と根拠）
## 実機チェックリスト（利用者向け・#352 へ）
- [ ] 操作手順 — 期待する見え方/手応え
## Issue 起票案（タイトル＋本文の下書き。起票は利用者確認後）
```

### 8. 締め

- 結果の要約（判定表＋🔴の数と内容）を利用者に報告。
- **Issue の起票・既存 Issue へのコメントは利用者の確認後**に行う（勝手に起票しない）。

## 原則

- **読み取り専用。** 監査は直さない。修正は結果を見て別途。
- **事実ベース。** 全指摘に file:line＋根拠（正典条項 or 物差し記号）。確証がなければ ℹ️＋要確認。
- **実機項目を推測しない。** コード・プレビューで確かめられないものは必ず実機チェックリストへ。
- **誤検出を出さない。** 各レビュア定義の「誤検出しない」節を尊重。敵対的検証を通ったものだけ利用者に見せる。
- 重大度記号はリポジトリ慣習（🔴 ブロッカー／🟡 直すべき／ℹ️ 軽微・要確認）。
