# 同梱するローカル LLM の作り方と記録（ADR-0051）

> ⚠️ **この資料は「作った記録」**＝同梱物の由来（元の重み・道具の版・手順）と、できたファイルの SHA-256 を残す。
> 版や手順を変えたら、`scripts/local-llm/build-model.sh` の固定値と**この表を一緒に**直す（再現できなくなる）。

## 手順

```bash
scripts/local-llm/build-model.sh <作業フォルダ（リポジトリの外）> Qwen/Qwen3.5-2B Qwen/Qwen3.5-0.8B
```

1. 公式の重みを Hugging Face から落とし、**配布元の SHA-256（LFS の oid）と照合**（合わなければ止める）。
2. 道具を**版を固定して**用意（llama.cpp の公式リリースの ZIP は SHA-256 を照合・ソースは同じタグのコミットを確かめる）。
3. 重み → GGUF（BF16）→ **Q4_K_M** へ量子化。
4. 同じ重みから**視覚の部品**（写真を読む `mmproj`）を **Q8_0** で変換（ADR-0052 決定4）。

- **判断：2B のまま**（ADR-0051 決定7 の「2B／0.8B を決める」）。0.8B は速く軽いが、入力を使わず例を写す＝構成案として使えない。⚠️ 専用化（段階4）の後なら 0.8B で足りる可能性はある＝そのとき測り直す。
- ⚠️ **出力が止まらない回が2回目**（2B・採用・素材あり）。上限（#1302）のおかげで 600 秒ではなく 207 秒で「長くなりすぎた」と言えた。止まらない回そのものを減らすのは段階4 の候補。

## 編集の途中の AI 補助の実測（ADR-0053・2026-10-01・最低検証機・2B Q4_K_M）

`scripts/local-llm/eval-assist.ts`（アプリと同じ指示文・本文）で、架空の3場面（採用の会社紹介・採用の働き方・社内発表）× 6 種類＝18 回。

| 版 | 候補が1つ以上出た | 語の途中で切れた候補 | 1回の時間 |
|---|---|---|---|
| 形で字数を縛る（`maxLength`＝上限） | 18／18 | **あり**（「…届けてい」「毎日多くの」） | 2〜10 秒 |
| 形の字数を緩める（上限×2）だけ | **14／18**（4回は全部の候補が上限越えで落ちた） | なし | 2〜10 秒 |
| **＋上限越えを文の終わり（。！？）で切る**（採用） | **18／18** | なし | **1〜7 秒** |

- ⚠️ **形（文法）で字数を縛ると、上限の字で語の途中で切られる**＝字数は守っても文として壊れる。2B は字数の指示をよく越えるので、**形は暴走よけの緩い上限**にし、**字数は検証で**見る。越えた候補は**上限の内側の最後の文の終わりで切る**（語の途中では切らない。切ると 8 字未満なら落とす）。
- 見出しは、何も言わないと「株式会社サンプル物流は地域の…」のような**文**になった→「文にしない・名詞で終わる」と指示して「配送会社」「先輩と3ヶ月研修」「問い合わせ対応時間を短縮」程度になった。
- 弱いところ（2B の限界）：「やわらかく」は元とほとんど変わらないことがある（元と同じなら落ちる＝「うまく候補を作れませんでした」）／「表示時間に収める」「セリフから作る」は2文目の内容を落としがち（文の終わりで切るため）／「研修を先輩と共有し」のような不自然な言い回しが時々出る。**選ぶのは利用者**なので、どれか1つ使えれば足りる設計にしてある。
- 会社名は印で渡して戻す＝18 回とも会社名は崩れなかった。数字と和文の間に空白が入る癖（「3 ヶ月」）は検証で詰める。

## ⚠️ アプリは縛りの形を並び替えて送っていた（#1403 の続き・2026-10-09・最低検証機・2B Q4_K_M）

**ここより上の点数は、アプリの実際の動きと違う**。道具（`eval-real-prompt.ts` など）は TypeScript から llama-server へ**直に**送るので、縛りの形（JSON Schema）は正典の順番のまま届く。一方アプリは Rust（`local_ai_generate`）を通り、`serde_json` が既定で**項目をアルファベット順に並べ替えていた**（#1286 で入れたときから）。AI は縛りの形の順に書くので、アプリでは：

- いちばん上が `parts`（`videoPlan` より先に場面を書く）
- 場面は `durationSec → sceneType → templateId → texts → assetRefs …` の順で、話す文（`narrationText`）が後回しになる
- その結果、**話す文を書かないまま同じ場面を繰り返す**（止まらない）か、話す文の無い短い案で終わる

実測（アプリが送った依頼＝`ai_last_request.json` をそのまま送り直した・`scripts/local-llm/replay-request.mjs`・出力の上限 1600・各 6 回）：

| 送ったもの | 正常 | 話す文がほとんど無い | 止まらない |
|---|---|---|---|
| アプリのまま（並び替わった形） | 1 | 1 | 4 |
| 同じ・同じ言葉の繰り返しを弱める設定（DRY） | 2 | 1 | 3 |
| **縛りの形だけ正典の順番に戻した** | **6** | 0 | 0 |

- 繰り返しを弱める設定は効かない（`repeat_penalty` は似せた入力で 5 回中 5 回とも話す文がほとんど無い案になり、逆効果）＝**採らない**。
- 直し方＝`serde_json` の `preserve_order`（`src-tauri/Cargo.toml`）。検査＝`local_llm::tests::request_keeps_schema_key_order`（外すと赤くなることを確かめた）。
- 写真の説明・編集の途中の手伝いも同じ口（Rust）を通るので、同じく並び替わっていた（いずれも直る）。
- ⚠️ **教訓**：似せた入力（その場で書いた道具・5 回とも成功）では再現しなかった。**アプリが送ったものそのもの**を残して送り直す（`ai_last_request.json`・`ai_prev_response.txt` を残すようにした）。
- **アプリで確かめた**（直した release 版・同じ入力）：
  - 1 回目は話す文のある健全な案（8 場面・生の合計 123 秒）だったが、当時の見張り（尺の 2 倍＝120 秒）に止められた。
  - 作り直した 2 回目で 4 場面・55 秒になり、「動画案ができました」まで進んだ（約 3 分 35 秒）。
  - → 長めの案は整える段が尺へ寄せるので、見張りの上限を**尺の 3 倍**に広げた（`AI_PLAN_RUNAWAY_DURATION_FACTOR`）。
