## 🔴 指摘（検証済み・重い順）

### 1. 書き出した MP4 から写真が抜ける（parity・CONFIRMED）

`src/app/store/timelineStore.ts:951`

書き出しがラスタライザへ**表示用 URL（`asset://…`）** をそのまま渡している。書き出しは SVG を Blob → `<img>` → canvas で焼く経路（`src/renderer/export/rasterize.ts`）で、**この経路は外部参照を読み込まない**（同ファイル冒頭が「素材画像は data URL でインライン済み」と前提を明記）。

- 検証で精密化された点＝**リクエストが遮断されるだけなので canvas は汚染されず `toDataURL` は成功する**。つまり**写真が抜けた MP4 が「動画を保存しました」として出る**（ADR-0026④に真正面から抵触）。
- プレビューが読めるのは、SVG を**トップ文書へ直接差し込んでいる**ため（同じ `assetSrcById` でも文脈が違う）。
- 場面形式は同じ理由で `asset://` を避け `readAssetDataUrl` で data URL 化している（`src/app/screens/ExportScreen.tsx:220-233`）。**守っていないのはタイムライン形式だけ**。
- **影響範囲**＝`assetSrcById` は文書を開く1か所で作られ、書き出しの入口も1本。**焼き出したプロジェクトも新規作成のプロジェクトも同じ**＝写真を含むタイムライン動画すべて。
- テストは `assetSrc: () => undefined` 固定（`buildTimelineFrames.test.ts:64`）＝この差を検出できない。

**修正の方向**：書き出し前に `doc.assets` を data URL のマップへ解決し、`assetSrc` はそれを引くだけにする。動画は `thumbnailPath` を使う規則も含めて、場面形式の `resolveExportSrc` と**共有関数に切り出して両形式で1つ**にする。フレームごとに読み直さない。

### 2. 焼き出した切り替えが効かない・キーフレームを置くと消える（correctness・実測つき）

`src/domain/timeline/bake.ts:760-761`

焼き出しが**同じ `targetId` に `ClipAnimation` を2本**作る（中間の場面は「入る側」と「出ていく側」の両方になる）。ところが**読む側は全員 `find` で1本しか見ない**（`renderer/timelineLayout.ts:223,288` ほか）。

- 実測（3場面・fade・凍結点 `f423d70`）＝`clip_002` に `anim_001`（入場 `[0,1]`）と `anim_002`（退場 `[4,5]`）の2本。
- 影響①：退場側が読まれず、**クロスフェードがハードカットになる**。
- 影響②：その部品にキーフレームを1つ置くと **`anim_002` が丸ごと消える**（`keyframeEdit` が `targetId` 一致を全除去してから1本書き戻すため）。
- **正典に `targetId` の一意性は書かれていない**（`11 §8` V26 は「実在を参照」だけ）＝「読む側が1本しか見ない」前提を実装だけが持っている。
- 傍証：`bake.test.ts:272` が `keyframes[0].opacity === 1` という**曖昧さを回避する条件**で検索しており、重複が意図ではなく漏れだったことを示す。

**修正の方向**：`bake` 側で `targetId` ごとに keyframes をマージして1本にする（入場 `[0,d]` と退場 `[outStart,outStart+d]` は時刻が重ならないので絵は変わらない）。あわせて **`animations[].targetId` の一意を V26 へ明記し `validateTimelineDoc` で検知**する。

### 3. 声を作っている最中に書き出しを始められる（error-state・resilience・CONFIRMED）

`src/app/store/timelineStore.ts:886-913`

開始前に見ているのは `isImporting`・`isOtherExportRunning`・`timelineExportBlockers`・`canExport` の4つだけで、`generatingVoiceClipId` を見ていない。場面形式は同じ入口で `isGeneratingNarration` を見て止めている（`ExportScreen.tsx:173`）。

- 合成が着地した時点で `commit` が `TIMELINE_EDIT_EXPORTING` で撥ねるので、**作った声はファイルだけ残り文書へ入らない**。MP4 はその読み上げが無いまま成功で終わる。
- 逆向き（書き出し中に声を作る）は塞いであり、**片側だけ**という非対称。
- 出る文言は「終わってから編集してください」で、**作った声が捨てられたことも、この MP4 にその声が入っていないことも伝えていない**。

### 4. 保存に失敗したままサイドバーで離脱すると編集が捨てられる（error-state・CONFIRMED）

`src/app/screens/TimelineProjectScreen.tsx:311-315, 331-348`

離脱の確認は画面内の「動画の一覧へ」にしか無く、サイドバーは素通し。アンマウント時の保存は `saveStatus === "idle"` のときだけ＝`error` のまま抜けると書かれない。

- 反証候補だった「store に `doc` が残るので戻れば残るのでは」は**成立しない**＝`navigation.ts` の `PROJECT_SCREENS` に `timeline-project` が無く、サイドバーの「今の動画」はこの画面へ戻らない。唯一の復路（一覧→開く）はディスクから読み直す。
- しかも `HomeScreen.tsx:171-172` はタイムライン形式を破棄確認から**明示的に除外**しているので、開き直す側でも聞かれない。

### 5. 色の面ドラッグに履歴の区切りが無い（resilience）

`src/app/screens/TimelineProjectScreen.tsx:992, 1054`

`ColorPicker` は自身の JSDoc に「境界が無いと**ひと撫でで数十〜百件**の履歴が積まれ上限を流し切る」と書いており、**他の13か所すべてが `onDragStart`/`onDragEnd` を渡している**のに、タイムライン編集の2か所だけ渡していない。この形式の履歴は**文書まるごとのスナップショット**なので、一撫でで 50 件（`HISTORY_LIMIT`）を埋める。

### 6. `Space`・`Delete`・矢印キーが無い（ux-model）

`src/app/screens/TimelineProjectScreen.tsx:409-430`

ADR-0034 **決定18** が明記しているのに未実装（`Escape`・`Ctrl+A`・`Ctrl+Z/Y` のみ）。`play`/`pause`/`removeSelectedClips`/`setPlayhead` はすべて実装済みで、**繋ぐだけ**。

⚠️ **段階0〜4 のどの表にも割り当てが無い**＝放置すると誰も拾わない。

### 7. 案内の指す先が存在しない（ui-terms・2件）

**(a) `TimelineProjectScreen.tsx:1623`** — 見た目パターンの差し込み口が動画専用で埋まらないとき「**別の見た目パターンを選んでください**」と言うが、この節には**テンプレそのものを差し替える操作が無い**（差し込み口の中身と文字しか触れない）。動画スロットを持つ見た目パターンは向きでしか絞られないので、置いた瞬間に到達しうる。

**(b) `TimelineProjectScreen.tsx:1932`** — 音が見つからない部品への「**音を選び直してください**」に対応する操作が無い。「選んだ部品→音」節は速さ・使い始め・音量・フェードだけで、**音源を選び直す欄が存在しない**。読み上げ側は「声を作る」で作り直せるので非対称。

いずれも ADR-0034 **決定5**（行き止まりの案内を作らない）に当たる。修正は「この部品を消して、『◯◯を置く』欄から入れ直してください」のように**実在する操作を名指しする**か、欄を足すか。

### 8. 開始秒・長さの数値欄が無い（ux-model）

`src/app/screens/TimelineProjectScreen.tsx:121, 935-950`

`NUDGE_SEC=0.5` の「前へ／後ろへ」と再生位置基準の「ここから／ここで終わる」という**独自操作**で代替しており、「3.0 秒ちょうど」に揃える手段が無い。中身・切り抜き・音・動きには `NumberField` があるので、**同じ画面で精密調整の流儀が2つ**。

⚠️ これも**段階2/3 のどちらの表にも入っていない**。

## ドライランとしての評価（#691）

**器は機能している。**

- 8観点すべてが起動し、`file:line` 付きの具体的な指摘を返した。観点ファイルの節をそのまま渡す設計（対象ファイル一覧＋該当節のみ）で、探索の暴走は起きなかった。
- **PR 単位のレビューでは出なかった「合成による破れ」が実際に拾えた**＝🔴1（#631 の書き出しと #712 の取り込みが個別には正しく、合わさって破れた）・🔴2（bake と keyframeEdit の前提のずれ）。
- 敵対的検証が**指摘を精密化**した（🔴1 は「書き出しが落ちる」ではなく「静かに欠落する」＝より悪い）。REFUTED ゼロは、レビュア定義の「誤検出しない」節が効いている傍証。
- correctness 観点は**実際にコードを走らせて計測**し、重複の実物を示した。

**改善点**

1. 観点ファイルを**監査直前に最新化する**運用が守られていない（今回は実装より前の版で回した）。
2. ux-model と error-state が**同じ事実を別々の重大度で挙げる**（隠し列の件）。司令塔での重複畳みは効いたが、観点ファイル側で担当を分ける余地がある。
3. **[プ] 項目のうち段階2 待ちのもの**（吸着・ズーム・ルーラー）は、未着手と分かっているのに毎回チェック対象に入る。観点ファイルに「段階」の列を足すと空振りが減る。
