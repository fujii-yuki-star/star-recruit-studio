## コンテキスト

α-4 で ADR-0018 の2モデル方式（場面正準＋時間軸射影＋場面アンカーのオーバーレイ層）を実装し、
α-5 では ADR-0023 で「射影の上に再生ヘッドと同期プレビューを載せる」方向で着手していた（#329 段階(1)(3) が landed）。

**利用者ヒアリング（2026-07-28）で、想定していた姿と実装方針の食い違いが判明した。**

- 利用者の想定＝**「場面形式 →（片道変換）→ タイムライン形式」で、変換後は完全に別物**。
  AI が関与するのは**変換前まで**なので、タイムライン側は AI 親和性を気にせず時間軸ネイティブでよい。
- 実装方針＝場面が正準のまま、タイムラインは**射影の上の補助編集面**（動かせるのは overlay だけ）。

**ADR-0018 が検討したのは3案（(A) 全面再設計 /(B) 読み取り専用 /(C) 2モデル）だけで、
「片道変換で別文書を作る」案は検討されていない。** (A) の不採用理由は「**AI が時間軸を吐く必要がある**」だったが、
**AI が変換前で切れるならこの理由は当たらない**。つまり本件は「決定済みだから却下」ではなく**未検討の設計判断**である。

さらに、**α-4 のタイムライン編集は利用者の動作確認対象に含まれていなかった**（実用的な実装ではなく、後で改修が入る前提だった＝
利用者申告）。したがって「既に検証済みの資産を壊す」という制約は無く、**方針を固めるなら今**である。

### 利用者が最重視するもの（2026-07-28・明示）

> **最重視は実装の大きさではなく、自由度。基本どんな動画でも作成できるところまで。**
> Premiere / Shotcut のようなソフトのイメージでよい。ただし**楽さもある程度保証**したいので、
> テンプレの枠なども素材として使えるようにする。

> **タイムラインは自由配置（FREE）のさらに拡張版**。基本的に常に空テンプレのようなもので、
> 字幕をどこにでも置け、動画もどこにでも置け、音声も出したいときに出したい尺で出せる。
> **そのボイスと字幕を紐づけて、この字幕はこのボイスのトラックと連動、ということも可能**。

## 判断軸

1. **自由度が最優先**（利用者明示）。「どんな動画でも作れる」を実装量より優先する。
2. **AI 親和性は上流で守る**（ADR-0007）。AI は場面形式だけを吐き、タイムライン形式には関与しない。
3. **プレビュー＝書き出しの一致は維持**（ADR-0001）。形式が増えても、この不変条件は落とさない。
4. **楽さの担保**：テンプレ（見た目パターン）を素材として持ち込め、差し込み口が生きていること。
5. **黙って壊さない**（`§2-5`）。片道変換でも**元のプロジェクトは残る**こと。
6. **段階出荷**：α-5 を再定義してでも、各段が単独で価値を持つこと。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) 現状維持＝ADR-0018/0023 の2モデルのまま育てる | 実装は軽い。だが**場面の枠を越えた自由配置・トラック自由化が原理的にできない**（正準が場面のため）。利用者の最重視項目（自由度）を満たさない。**不採用** |
| (B) 場面モデルを時間軸ネイティブへ**全面移行**（ADR-0018 の (A) 再考） | 自由度は最大。だが**AI 出力・テンプレ・既存プロジェクトの全経路を作り替える**。AI が時間軸を吐く必要が生じ ADR-0007 を壊す。**不採用** |
| **(C) 片道の「焼き出し」で別プロジェクト形式を新設【採用】** | 場面形式（AI・テンプレ・簡易編集）は**そのまま残す**。そこから**新規のタイムラインプロジェクトを作成**し、以後は時間軸ネイティブで自由に編集する。AI は変換前で切れるので (B) の障壁が無い。**元プロジェクトが残るので不可逆の痛みが無い**（作り直したければ焼き直して別の新規を作る）。**採用** |

## 決定（Accepted）

> **「タイムラインプロジェクト」を、場面形式とは別の文書形式として新設する。場面形式プロジェクトから
> 片道で焼き出して新規作成し、以後はそちらで時間軸ネイティブに編集する。元の場面形式プロジェクトは残る。
> 焼き直しは常に別の新規プロジェクトを作る（差分マージはしない）。AI が関与するのは場面形式まで。**

### 位置づけ（利用者の言葉を設計語へ）

**タイムラインプロジェクト＝「FREE 自由配置（空間の自由）× タイムライン（時間の自由）」を最初から両方持つ文書。**
場面という区切りを持たず、キャンバスは常に自由配置。テンプレは**置ける素材のひとつ**であって枠ではない。

### 場面形式の「凍結」範囲（2026-07-28 決定）

「場面形式は凍結寄り」を**画面単位で**適用すると、**両形式で共有する土台まで止まってしまう**（テンプレ・素材・声・
書き出しの核は、タイムライン形式でもそのまま使う）。よって**変更の種類**で線を引く。

**続ける（凍結しない）**
1. **不具合修正**（当然）。
2. **AI 生成の品質**（プロンプト・検証・自動補正）＝場面形式にしかない資産で、**タイムライン形式の入力の質**でもある。
3. **テンプレ（見た目パターン）の追加・改善**＝タイムライン形式でも**素材として使う**ので、投資が両方に効く。
   テンプレ作成エディタも同様。
4. **素材まわり・声（VOICEVOX）**＝両形式が共有する土台。
5. **書き出しの共通核**（`layoutScene`・パリティ・コーデック）＝両形式が共有する。
6. **文言・エラー・操作性の質**（`§2-3`/`§2-5`）＝アプリ全体の品質。

**凍結する（新機能を足さない）**
1. **場面編集画面の編集機能の拡張**（新しい体裁項目・新しい配置操作・新しいアニメ種別 等）。
2. **時間軸まわり**（タイムライン形式でやる）。
3. **場面形式専用の新概念**＝`project.schema.json` の Scene に新フィールドを足すこと。

**判断が分かれるもの → 凍結側に倒す**
- **FREE 自由配置の機能拡張**：FREE は本形式の**前身**なので、強化するとタイムライン側と二重投資になる。
  ただし**タイムライン側で作った部品を FREE へ流用できる**場合は、その限りではない。
- **キーフレーム（#512 高度アニメ）**：タイムライン形式の機能として作る。場面形式側では拡張しない。

> 📌 凍結は「触らない」ではなく**「新しい編集能力を場面形式に足さない」**の意。既存 Issue の仕分けは Issue 再編で行う。

### 声と字幕の連動（利用者要望・本形式の特徴）

**音声クリップと字幕クリップを紐づけられる**＝「この字幕はこのボイスのトラックと連動する」。
ADR-0029（FREE 字幕の `subtitleSource`）で作った「字幕は対象から解決する」考え方を、
**場面内の行**ではなく**タイムライン上の音声クリップ**へ向け直したもの。具体形は未解決（下記）。

## 結果・影響

### コード

- **新設**：タイムラインプロジェクトの文書モデル（domain）・編集画面・書き出し経路。
- **共有**：1枚のフレームを描く核（`layoutScene` 系）は**両形式で共有**する＝パリティ（ADR-0001）を二重に作らない。
  違うのは「並べ方」だけ（場面の順番 vs 時刻とトラック）。**一般合成は #431（複数動画スロット・zIndex 順）で
  一部先行しているので、ゼロからではない。**
- **焼き出し**：場面形式 → タイムライン形式の変換（片道）。ADR-0030 の `freeLayoutFromPlacedContent`
  （通常→FREE の内容移送）と同じ系統の処理を、時間軸へ拡張する形になる見込み。
- **廃止**：場面形式の編集用タイムライン画面（`TimelineEditScreen`）と `timelineOverlay`。
  読み取り専用の `TimelineScreen` は残す。
- **見直し**：#329 段階(1)(3)（再生ヘッド・編集元への導線）は**タイムライン側で作り直す**。
  `playheadFrameAt` など時刻解決の純粋関数は流用できる見込み。

### 正典

## 未解決の論点

> **棚卸し（2026-08-17・Accepted 化と同時）**＝下記8項目は**すべて決着済み**。決着した項目は取り消し線と
> 決定先（Issue 番号）で示す。**α-5 に残っている実装**は論点ではなく作業なので、ここではなく #697
> （ロードマップ）と #512（タイムライン形式の動画素材）で追う。**#512 はクローズ済み**＝直接置き（段1・段2）と
> 差し込み口（段3・段3b）は映って元の音も鳴り、**立ち絵に入れた動画だけ**が静止画のまま（置いてあると
> 書き出しの手前で断る）＝そこは **#809（α-6）** で追う。


1. ~~**文書モデルの具体形**~~ → **決定（#627）**。`11 §7.6` 参照。**クリップ＝「FREE 要素 ＋ 時間（trackId/startSec/durationSec）」**
   ＝空間の語彙は `FreeElement`（ADR-0008）と同じものを使う（描画は `layoutScene` の FREE 分岐を共有＝パリティを二重に作らない）。
   テンプレ由来クリップは **Scene 相当を内包しない**＝`kind:'template'` のクリップが `templateId`＋差し込み口
   （`assetRefs`/`texts`/`textStyles`/`slotFits`）だけを持つ（場面という入れ子を作らない）。
   **クリップごとの `zIndex` は持たない**＝重ね順は tracks の並び順だけで決まり、そのために
   **同一トラック内で時間の重なりを禁止する**（`11 §8` V24。重ねたいならトラックを足す）。
2. ~~**スキーマの置き場**~~ → **決定（#627）**。**`timeline-project.schema.json` を新設**する（`project.schema.json` の拡張ではない）。
   版は**独立**（初期 `"1.0"`・場面形式の 1.x バンプに釣られない）＝「1つの schemaVersion で2形式」を避ける。
   **形式の判別はトップレベル `format`**＝**`"timeline"` か否かの一点**で、`projectId` の採番は両形式共通（`11 §1`・`§2.1`）。
   **場面形式のファイルは `format` を書かない**（不在＝場面形式。`project.schema` は `additionalProperties:false` ゆえ
   `format:"scene"` は検証を通らない＝CI の must-reject で固定）。`ProjectFormat` の `"scene"` は読込時の解決値

### 決定19：場面の切り替え（トランジション）は**キーフレームで表す**。専用の入れ物は持たない（2026-07-28・#628）

**経緯**：利用者は当初「両方（基本はキーフレーム・`wipe` のために専用の入れ物も持つ）」を選んだが、その前提となった
私の説明が不正確だった。調査の結果、**`TRANSITION_TYPES` の5種のうち `wipe` と `zoom` は現状どこにも描画されておらず
`fade` に丸められている**（`sceneTransitions.ts` の MVP 対応表＝「これ以外（wipe/zoom）は fade にフォールバックする」／
Rust 側も `validate_xfade_name("wipe") == None`）。事実を伝えたうえで**利用者が α-6 送りを決定**。

**決定**：
1. **タイムライン形式は切り替え専用の入れ物を持たない。** 実際に描かれる `fade`/`slide` は既存のキーフレーム
   （不透明度・位置）で表せる＝運ぶべき情報がゼロの入れ物を先に作らない（YAGNI）。同じことに2通りのやり方を
   作らない（ADR-0026②）。
2. **#634「トランジションの自由配置」は、キーフレームの傾斜を自由に置けることで満たす。**
3. **専用の入れ物は「`wipe` を実際に描けるようにする」ときに、マスクと同時に検討する**（α-6。#634 は既に
   マスクを対象外＝α-6 としている）。additive なので後から入れられる。
4. **焼き出し（#628）は「設定された切り替え」ではなく「実効の切り替え」（`resolveTransition` の結果）を落とす。**
   ＝**現に見えている絵と一致**するので、`wipe` 設定の場面を `fade` として焼くのは「黙って差し替え」ではない
   （もともと `fade` で描かれている）。

**取りこぼし防止（構造で担保）**：α-6 で `wipe` が本当に描けるようになった瞬間、焼き出しが黙って `fade` へ
落とすと §2-5／ADR-0026④違反になる。これを人の注意に頼らないため、**焼き出しの分解は実効の切り替え種別に対して
網羅的にし、網羅漏れがコンパイルエラーになる形（exhaustive check）で書く**。`sceneTransitions` の丸め表から
`wipe` が外れた時点でビルドが落ち、対応を強制される。

**再検討の条件**：`wipe`（またはマスクを要する切り替え）を実際に描けるようにするとき。

### 決定24：字幕は**読み上げクリップを1つ指す**（文言と時間が追従する）（2026-07-29・#633）

未解決4「声と字幕の連動の具体形」の決着。**字幕クリップが読み上げクリップの id を持つ**
（`TimelineClip.voiceClipId`・schema 1.2＝任意追加）。

**なぜ参照（グループではない）か**：グループは「まとめて動かす」もので**向きが無い**（どちらが元か決まらない）。
連動は「字幕が読み上げに従う」＝一方向なので、参照のほうが意味に合う。形も ADR-0029 の `subtitleSource`
（FREE 字幕が対象を1つ指す）と同じで、**場面の中のセリフ**だった対象を**タイムライン上の読み上げ**へ
向け直したものになる（#526 の概念をここへ継承）。

**連動が担うのは2つ**：
- **文言**＝指した読み上げの文を出す。字幕クリップ自身に文が入っていれば**そちらが優先**
  （言い換え用の上書き層＝ADR-0029 (2b) と同じ流儀）。
- **時間**＝「連動している＝**区間が一致している**」を保つ（動かす・伸ばす・連動を始める、のどれでも同じ区間へ）。
  **字幕側から時間を変えることはできない**＝「連動する」と言ったのに位置がずれたまま、を作らない。

**壊れた参照は黙って消さない**（§2-5）＝検証（`11 §8` V29）が知らせる。字幕自身の文があればその文で
描かれ続けるが、**文が無ければ何も出ない**ので、その字幕は**書き出しの手前で止める**（ADR-0026④）。**片方だけ動いた結果も作らない**＝字幕を置けない場所へ動かすことになる
操作は、読み上げ側の移動ごと断る。

**掛け合い・同時2ボイスに専用概念は要らない**（決定8）＝声も字幕も**列を分ける**だけ。場面形式の
`startWithPrevious`（ADR-0031）や帯の積み上げ（`stackedSubtitleBands`）に当たるものは、
**列の並びがそのまま担う**。

### 決定23：「バラす」は**戻せない**（取り消しでだけ戻る）＋前後で絵が変わらない（2026-07-29・#632）

未解決6「『バラす』の可逆性」の決着。

- **戻せない。** バラした後の部品から元の見た目パターンは組み立て直せない（どの部品がどの差し込み口だったかを
  持たないうえ、バラした後は部品を自由に動かせる）。**取り消し（Ctrl+Z）でだけ戻る。**
- したがって**操作の前に断る**（`§2-5`）＝「見た目は変わらないが、写真や文字を入れる場所は無くなる。戻すときは
  取り消しを押す」を確認で示す。
- **バラす＝表現の変更であって、見た目の変更ではない**（完了条件）。だから変換は描画と同じ材料を通す：
  クリップ→`Scene`（`sceneFromClip`）→層ごとの要素（`freeLayoutFromPlacedContent` の `faithful`＝
  **描かれるものすべて**を写す）。**別の規則を書き起こさない**（§6）。
- 守り方は**描いた結果の比較**（`explodeParity.test.ts`）＝変換の書き方を変えても「絵が変わらない」だけは残る
  （ADR-0001 のパリティと同じ考え方）。

### 決定22：タイムラインの書き出しは**常に全フレーム描画**（ハイブリッドへ倒さない）（2026-07-29・#631）

未解決5「ハイブリッドの境界（どの条件でフレーム描画へ倒すか）」の決着。**条件を作らず、常に全フレーム描く。**

**理由**：
1. **帯分割（`videoSceneSplit`）が合成の単位を跨いで切る。** 決定19 の前提（`fade` は `xfade=fade` と同値＝
   **1枚に合成してから α**）は、クリップの中身を下/中/上へ割ると崩れる（層ごとに α が掛かる／クリップ全体の
   フェードが動画スロットへ乗らない）。#631 の PR でこの構造を確認済み（`11 §7.6.4` に警告として記載）。
2. **判定条件を増やすほどパリティの検査点が増える。** 「重なり・アニメ・速度・クロップの有無」で経路が分岐すると、
   プレビューと書き出しの一致（ADR-0001）を条件の組み合わせぶん確かめることになる。全フレームなら
   **`layoutTimelineAt(doc, t)` を並べるだけ**＝プレビューと同じ1経路。
3. 決定10 が既に「**迷ったら全フレーム描画を優先＝確実な出力を取る**」としている。本件はまさにその場合。

**引き換えに失うもの**：書き出し時間。場面形式が「動きの無い場面は静止1枚」で稼いでいた分は使えない。
**再検討の条件**：実測で許容できない遅さになったとき。そのときは「重なりもアニメも速度変更も無いクリップだけの
区間」を静止1枚へ倒す形を、**パリティの検査を足したうえで**入れる。

### 決定21：再生中は編集しない（編集・取り消しで再生を止める）（2026-07-28・#630）

ADR-0023 は「**再生しながら複数トラックで編集**」を掲げていた。本形式で再生（#630）を実装したところ、
**位置を使う操作と両立しない**ことが分かった：「再生位置へ」「ここから始める」「ここで終わる」は
再生ヘッドの値を掴むので、走っている最中に押すと**同じ操作の結果が毎回変わる**（ADR-0026①「設定した
意味どおり」に反する）。

**決定**：
1. **編集・取り消し・やり直しをしたら再生を止める。**
2. **位置を使う操作は再生中に押させない**（理由を出す＝§2-5）。位置を使わない操作（列を足す等）は
   押せるが、押した時点で再生は止まる。

**再検討の条件**：再生しながらの編集が実際に要るとき（例：音に合わせて切りたい）。そのときは
「押した瞬間の位置で固定する」など、結果が一意に決まる形を設計してから開ける。

### 決定20：焼き出しの分解規則（2026-07-28・#628 変換）

`bakeTimelineProject`（`src/domain/timeline/bake.ts`）の対応表は **`11 §7.6.1`** に置く（正典はそちら）。
ここには**なぜそう分解したか**だけを残す。

1. **列（トラック）の割り当ては「1場面ぶんを連続した並びで取り、空いた列は下から詰め直す」。**
   連続で取るのは、切り替えで重なる2場面の層が**互い違いに挟まらない**ようにするため＝どちらかが丸ごと手前になり、
   切り替えを「場面まるごとの不透明度」で表せる（決定19）。**入る側を常に手前へ固定はしない**＝それをやると
   切り替えのたびに列が1本ずつ増え、際限が無くなる。代わりに `fade` の**付け先を手前側にする**
   （入る側が手前なら 0→1／出ていく側が手前なら 1→0）。どちらも xfade の線形ブレンドと同値なので絵は変わらない。
2. **`slide` は両方が一緒に動く。** FFmpeg の `slideleft` 等は A が抜けて B が入る形で2枚とも移動するため、
   入る側だけ動かすと絵が変わる（＝「同じ絵になる」の完了条件を外す）。この形なら重ね順に依存しない。
3. **切り替えの付け先は「場面を代表する対象」**＝通常はテンプレクリップ、FREE は**場面グループ**。
   FREE で要素ごとに不透明度を書くと、要素が自前で持つ不透明度を潰す（グループなら乗算＝ADR-0019 (3)）。
4. **読み上げ文が空の行はクリップにしない。** schema の `if/then` が `kind:'voice'` に中身を要求しており、
   鳴らない「空の声」を作らないため（`11 §8` V28 と同じ判断）。
5. **素材は「焼く範囲で実際に使うもの」だけ持っていく**（`sceneActiveAssetIds`）＝差し込み先を失った休眠の割当
   （ADR-0030）まで運ぶと、コピー容量が実態とずれる（決定13 の「容量を焼く前に伝える」が嘘になる）。
6. **FREE の場面にも見た目パターンのクリップを最背面に置く。** 決定1では「FREE＝要素ごとのクリップ」とだけ
   決めていたが、**FREE テンプレ（`free_canvas_v1`）も `background` 層を持っており動画に出ている**。
   要素だけ焼くと背景が丸ごと落ちる。描画（`layoutScene`）が「category を問わず層を描いてから自由配置を重ねる」
   のと同じ形にする＝決定1 の追補。場面グループにはこのクリップも入れる（まとめて動かすと背景ごと動く）。
7. **自由配置かどうかは「見た目が解決できればその category、できなければ場面の記録（`sceneType`）」。**
   見た目だけで決めると、**見た目が見つからない場面**（ユーザーテンプレ削除後など）の `freeLayout`・グループ・
   場面内アニメが黙って落ちる。かといって `sceneType` だけで決めると、通常テンプレに残った**休眠 `freeLayout`**
   （ADR-0030）を焼いてしまい描画と食い違う。**解決できるときは描画と同じ規則・できないときだけ多く持つ側**
   （ADR-0030 系の方針）へ倒す。
8. **持っていけないものは黙って落とさず返す**（`BakeNote`・`15 §6` の `BAKE_*`）。現時点で2つ。
   - **行に追従する字幕**。本形式に「対象（`subtitleSource`・ADR-0029）」の語彙が無いため（連動は #633）。
     **時間で変わらないものは焼く**＝セリフ列の無い場面のテンプレ字幕（`texts` で出る）と、FREE の字幕ボックスで
     対象＝読み上げのもの（いま出ている文を `text` に焼き付ける）。**行数では判定しない**＝`lines` が1行でも
     テンプレ字幕層は行の字幕へ差し替わるので、行数で見ると取りこぼす。判定は**実際に表示されているものだけ**。
   - **動画の差し込み口の再生開始タイミング**（ADR-0027 の `slotVideoStart`＝本形式に置き場が無い）。

## 追補：音量キーフレームの持ち方と、書き出しでの一致（#512・2026-08-03 設計 → **実装済み**＝timeline schema `"1.7"`）

**やりたいこと**＝音のクリップ（読み上げ／BGM・持ち込み）の音量を**時間で変える**（いまはクリップ単位の
一定値＋前後フェードだけ）。ADR-0019 (4) の「音量KF」を、タイムライン形式の語彙として置き直す。

### 置き場（決定案）

**`TimelineClip.volumePoints?: { timeSec: number; volume: number }[]`**（クリップの先頭からの秒・0〜1.5）。
- **絵のキーフレーム（`ClipAnimation`）とは別に持つ**＝`Keyframe` は場面形式と `$defs` を共有していて
  （`11 §1`）、絵の語彙に音量を足すと**場面形式の凍結側**へ意味の無いプロパティが増える。音は
  `ClipAnimation` の対象（クリップ／グループの変形）とも合わない。
- **タイムライン形式だけの語彙**（`FreeElement`／`Keyframe` には足さない＝`crop` と同じ扱い）。
- 既存の `volume`（一定値）と `fadeInSec`/`fadeOutSec` は**そのまま**＝`volumePoints` が無いときの意味は不変。
  両方あるときは **`volumePoints` が基準の音量を置き換え、フェードはその上に掛ける**（＝いまの
  `fadedVolume` の「基準×フェード係数」の形を保つ）。規則を1つにすることで再生・書き出しが同じ式になる。

### 書き出しでどう一致させるか（**決定＝案A・利用者判断 2026-08-03**）

再生は JS で線形補間すればよい。書き出しは FFmpeg なので、同じ曲線を**フィルタで**作る必要がある。

- **案A：`volume` の式**（`volume='<expr>':eval=frame`）＝点列から `if(lt(t,..),..)` の入れ子を組む。
  1本のフィルタで済むが、**式の評価が FFmpeg 側**なので「プレビューと同じ値か」をテストで直接確かめられない
  （確かめるには式の評価器をテスト用に自作することになる）。
- **案B：区間ごとに `volume` を掛け直す**＝点間を `asplit`/`atrim`＋`volume`＋`concat` で繋ぐ。
  各区間は一定値になるので**階段状**になり、なめらかに変わらない（意味が変わる＝ADR-0026①に反する）。
- **案C：点間ごとに線形の式を持つ短い `volume` を並べる**（区間ごとに `volume='a+b*(t-t0)':eval=frame`）。
  案Aの入れ子を避けつつ曲線は正確。ただしフィルタ数が点の数だけ増える。

**推奨＝案A**。理由＝(1) 音の合成は既に1本の filter_complex に集約されていて、区間分割は
`planBgmMix` の配置・フェードと二重管理になる (2) 式は**点列から純粋関数で組む**ので、
プレビューの `volumeAt(points, t)` と**同じ点列・同じ規則**から作れる (3) 検算は
「式の文字列が期待どおり」＋「代表時刻で `volumeAt` が期待値」の二方向で守れる（**式そのものの評価器は作らない**）。

**決定＝案A**（利用者判断 2026-08-03）。「FFmpeg の式が本当に同じ曲線を出すか」は**テストでは式の形までしか
見られない**ので、**実機で音を聞いて確かめる**ことを受け入れる（案C のフィルタ増を避ける）。
そのぶん**式は点列から純粋関数で組み、点列そのものは再生と共有する**＝ずれるとしたら「式の書き方」だけに
閉じ込める。実機確認は書き出しの段（下記3）の完了条件に含める。

### 段取り（**実施済み**＝下記1〜3.5 は land 済み）

1. ✅ schema（timeline 1.7・additive）＋ `volumeAt`（`domain/timeline/audio.ts`・純粋）＝**点の間は線形・点の外は端の値で伸ばす**（区間外で黙って 0 や 1 に化けない）・**並びに依存しない**（読み込んでから並べ替える）
2. ✅ 再生（`fadedVolume` の基準を `volumeAt` 経由へ＝**フェードはその上に掛かる**・点が無ければ従来どおりクリップ一定）
3. ✅ 書き出し（**式は front の `volumeExpr`〔domain・純粋〕が点列から組み、`BgmRunInput.volumeExpr` で渡す。Rust は `volume='<式>':eval=frame` として差し込むだけ**）／⏳ **実機で音を確認するのは残り**
   - 設計時は「点列を渡し Rust が式を組む」と書いていたが、**組むのは front だけ**にした＝規則が2か所に散らないので、ずれうる点が「式の書き方」だけに閉じ込まる（上の (2)(3) の理由をそのまま満たす）。
   - 式の `t` は**その音の先頭からの秒**（`asetpts` で 0 起点へ戻し `atempo` を掛けたあとの時刻）＝再生の `volumeAt(points, 局所秒)` と同じ物差し。フェード（`afade`）は従来どおり**式の上に**掛かる。
   - **点が無いクリップには渡さない**（キーごと落とす）＝場面形式を含む従来の呼び出しは `volume=<一定値>` のまま＝**出力不変**。
   - **`t` の基準は同梱 ffmpeg の実測で確かめた**（`/canon-check` 2026-08-03）＝`atrim=5:9`→`asetpts`→`atempo=2`→`volume='…':eval=frame` で局所秒 1.0／3.0 の実測ゲインが `volumeAt` の期待値（0.4／0.8）と一致。**速度・トリムを掛けても `t` は「クリップ先頭からの秒」のまま**で `afade` と同じ物差しだった。残るのは「音として聞く」確認。
3.5. ✅ **段3 の後始末**（`/canon-check` の 🟡＋ℹ️2 を潰す・2026-08-03）
   - **点の数には上限がある**（`VOLUME_POINTS_MAX = 60`・`domain/constants.ts`）。**好みで決めた数ではなく、FFmpeg の式の解析に上限がある**ため。同梱 ffmpeg での実測＝**点 95 個までは通り 96 個で解析に失敗する**（`[Eval] Missing ')' or too many args`）。**境目の正確な位置は式に書かれる数の桁数で少し動く**（入れ子の `if()` で組んだ式では 97 個で失敗し 98 個は通る、という単調でない並びも観測した）ので、**上限は余裕を取った値**にする。渡してから落ちるとフィルタの組み立てごと失敗し、出せるのは「もう一度お試しください」＝**何度やっても成功しない案内**（§2-5・ADR-0026④）なので、**`timelineExportBlockers` が押す前に断る**（`TIMELINE_EXPORT_VOLUME_POINTS_TOO_MANY`・`15 §6`）。数えるのは**正規化した後**（同じ時刻の重複は式に出ない）。
     - **式は入れ子をやめて「区間ごとの項の足し算」にした**（各時刻でちょうど1つの項が 1 倍・残りは 0 倍。区間は半開 `gte`〜`lt` で境界を取り合わない）。**これは上限を無くす手ではない**（足し算でも同じあたりで頭打ち＝解析の予算は深さだけでなく式全体に効く）。**読みやすさと、上限の位置が点の数に素直に比例すること**のために採る（入れ子の式は境目が単調ですらなかった）。
     - **式へ書く数は12桁に丸める**（`0.19999999999999998` → `0.2`）＝式の長さが倍近く変わり、**渡せるコマンドラインの長さ**（Windows で約32000文字・音の本数ぶん積み上がる）に早く当たるため。動くのは 1e-12＝聞き分けられない。
   - **点列の正規化を再生と書き出しで共有する**（`normalizedVolumePoints`＝並べ替え・**同じ時刻の重複を落とす**・値域へ収める）。これで ℹ️ 2件は**構造的に**消える：
     - 重複していた時刻ちょうどの値が、再生は手前の点・式は次の点を採って**逆になる**問題（`<=` の早期 return と `lt()` の分岐の差）。
     - **クランプの順序が1段ずれる**問題（生値で補間してから収める／収めてから補間する＝値域外の点で中間の値が食い違う）。入口で収めるので両者が同じ側に立つ。
   - **実測でパリティを確認**＝`atrim=5:25`→`asetpts`→`atempo=2`→`volume='…':eval=frame` の並びで、局所秒 0/1/2/3/5/8 の実測ゲインが `volumeAt` の期待値（0.2/0.4/0.6/0.8/0.75/0.5）と一致（`volumedetect` の 0.1dB 刻みの範囲で）。
4. ✅ 画面（音の部品パネルに「音量の変化」＝再生位置に点を置く・キーフレームの UI と同じ流儀）
   - 編集は `domain/timeline/volumePointEdit.ts`（純粋＝置く・直す・外すだけ・規則は `11 §7.6.3.2`）。
     **編集層でも上限（`VOLUME_POINTS_MAX`）と「同じ時刻には1つ」を課す**（キーフレームと同じ＝`§7.6.3.1`）＝**置く前に断る**（書き出しの手前の停止は、手で書いた文書のための保険として残す）。
   - **値域は編集層でも守る**（schema の 0〜1.5＝正規化が入口で収める）。**鳴る音を持たない部品には置かせない**。
   - 画面は `06 §12.1`（再生位置に置く・置いた点は**動画の時刻**で一覧・この位置へ／外す／すべて外す・
     **再生位置が部品の外なら鳴っている時間を示して案内**・**上限では理由を出す**・再生中と固定した列では触れない）。
   - **「段3 の実機確認より前に画面を出さない」の順序について**＝この決めは「点を置けるのに書き出しへ効かない」を
     避けるためのもので、**段3 が land し実測でも一致した時点でその危険は無い**。むしろ**画面が無いと利用者は
     音を聞いて確かめられない**（点を置く手段が無い）ので、順序を入れ替えて画面を先に出した。
     **残るのは「音として聞く」確認だけ**（⏳）。
