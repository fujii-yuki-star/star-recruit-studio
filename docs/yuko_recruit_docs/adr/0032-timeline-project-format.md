# ADR-0032: タイムライン編集を「別プロジェクト形式」として新設する（場面形式から片道で焼き出し）

- **状態**: Proposed（2026-07-28・利用者ヒアリング完了／実装は α-5 再定義後）
- **日付**: 2026-07-28
- **関連**: [`adr/0018`](0018-cross-scene-timeline-model.md)（2モデル方式＝**本ADRが一部 supersede**）/ [`adr/0023`](0023-integrated-timeline-editing.md)（統合タイムライン編集＝**本ADRが置き換え・段階(1)〜(9) は再編**）/ [`adr/0024`](0024-non-destructive-editing-model.md)（非破壊編集・素材＝源泉・自己完結）/ [`adr/0008`](0008-free-layout.md)（FREE 自由配置＝**本形式の空間モデルの前身**）/ [`adr/0019`](0019-keyframe-animation-model.md)（per-frame 描画）/ [`adr/0001`](0001-rendering-parity.md)（プレビュー＝書き出し）/ [`adr/0007`](0007-ai-pipeline.md)（単一パイプライン・AI 親和性）/ `CLAUDE.md §2-4`（テンプレ駆動）・`§10`（本格タイムライン編集）・`§11`

## コンテキスト

α-4 で ADR-0018 の2モデル方式（場面正準＋時間軸射影＋場面アンカーのオーバーレイ層）を実装し、
α-5 では ADR-0023 で「射影の上に再生ヘッドと同期プレビューを載せる」方向で着手していた（#329 段階(1)(3) が landed）。

**利用者ヒアリング（2026-07-28）で、想定していた姿と実装方針の食い違いが判明した。**

- 利用者の想定＝**「場面形式 →（片道変換）→ タイムライン形式」で、変換後は完全に別物**。
  AI が関与するのは**変換前まで**なので、タイムライン側は AI 親和性を気にせず時間軸ネイティブでよい。
- 実装方針＝場面が正準のまま、タイムラインは**射影の上の補助編集面**（動かせるのは overlay だけ）。

**ADR-0018 が検討したのは3案（(A) 全面再設計 /(B) 読み取り専用 /(C) 2モデル）だけで、
「片道変換で別文書を作る」案は検討されていない。** (A) の不採用理由は「**AI が時間軸を吐く必要がある**」だったが、
**AI が変換前で切れるならこの理由は当たらない**。つまり本件は「決定済みだから却下」ではなく**未検討の設計判断**である。

さらに、**α-4 のタイムライン編集は利用者の動作確認対象に含まれていなかった**（実用的な実装ではなく、後で改修が入る前提だった＝
利用者申告）。したがって「既に検証済みの資産を壊す」という制約は無く、**方針を固めるなら今**である。

### 利用者が最重視するもの（2026-07-28・明示）

> **最重視は実装の大きさではなく、自由度。基本どんな動画でも作成できるところまで。**
> Premiere / Shotcut のようなソフトのイメージでよい。ただし**楽さもある程度保証**したいので、
> テンプレの枠なども素材として使えるようにする。

> **タイムラインは自由配置（FREE）のさらに拡張版**。基本的に常に空テンプレのようなもので、
> 字幕をどこにでも置け、動画もどこにでも置け、音声も出したいときに出したい尺で出せる。
> **そのボイスと字幕を紐づけて、この字幕はこのボイスのトラックと連動、ということも可能**。

## 判断軸

1. **自由度が最優先**（利用者明示）。「どんな動画でも作れる」を実装量より優先する。
2. **AI 親和性は上流で守る**（ADR-0007）。AI は場面形式だけを吐き、タイムライン形式には関与しない。
3. **プレビュー＝書き出しの一致は維持**（ADR-0001）。形式が増えても、この不変条件は落とさない。
4. **楽さの担保**：テンプレ（見た目パターン）を素材として持ち込め、差し込み口が生きていること。
5. **黙って壊さない**（`§2-5`）。片道変換でも**元のプロジェクトは残る**こと。
6. **段階出荷**：α-5 を再定義してでも、各段が単独で価値を持つこと。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) 現状維持＝ADR-0018/0023 の2モデルのまま育てる | 実装は軽い。だが**場面の枠を越えた自由配置・トラック自由化が原理的にできない**（正準が場面のため）。利用者の最重視項目（自由度）を満たさない。**不採用** |
| (B) 場面モデルを時間軸ネイティブへ**全面移行**（ADR-0018 の (A) 再考） | 自由度は最大。だが**AI 出力・テンプレ・既存プロジェクトの全経路を作り替える**。AI が時間軸を吐く必要が生じ ADR-0007 を壊す。**不採用** |
| **(C) 片道の「焼き出し」で別プロジェクト形式を新設【採用】** | 場面形式（AI・テンプレ・簡易編集）は**そのまま残す**。そこから**新規のタイムラインプロジェクトを作成**し、以後は時間軸ネイティブで自由に編集する。AI は変換前で切れるので (B) の障壁が無い。**元プロジェクトが残るので不可逆の痛みが無い**（作り直したければ焼き直して別の新規を作る）。**採用** |

## 決定（Proposed）

> **「タイムラインプロジェクト」を、場面形式とは別の文書形式として新設する。場面形式プロジェクトから
> 片道で焼き出して新規作成し、以後はそちらで時間軸ネイティブに編集する。元の場面形式プロジェクトは残る。
> 焼き直しは常に別の新規プロジェクトを作る（差分マージはしない）。AI が関与するのは場面形式まで。**

### 位置づけ（利用者の言葉を設計語へ）

**タイムラインプロジェクト＝「FREE 自由配置（空間の自由）× タイムライン（時間の自由）」を最初から両方持つ文書。**
場面という区切りを持たず、キャンバスは常に自由配置。テンプレは**置ける素材のひとつ**であって枠ではない。

### 場面形式の「凍結」範囲（2026-07-28 決定）

「場面形式は凍結寄り」を**画面単位で**適用すると、**両形式で共有する土台まで止まってしまう**（テンプレ・素材・声・
書き出しの核は、タイムライン形式でもそのまま使う）。よって**変更の種類**で線を引く。

**続ける（凍結しない）**
1. **不具合修正**（当然）。
2. **AI 生成の品質**（プロンプト・検証・自動補正）＝場面形式にしかない資産で、**タイムライン形式の入力の質**でもある。
3. **テンプレ（見た目パターン）の追加・改善**＝タイムライン形式でも**素材として使う**ので、投資が両方に効く。
   テンプレ作成エディタも同様。
4. **素材まわり・声（VOICEVOX）**＝両形式が共有する土台。
5. **書き出しの共通核**（`layoutScene`・パリティ・コーデック）＝両形式が共有する。
6. **文言・エラー・操作性の質**（`§2-3`/`§2-5`）＝アプリ全体の品質。

**凍結する（新機能を足さない）**
1. **場面編集画面の編集機能の拡張**（新しい体裁項目・新しい配置操作・新しいアニメ種別 等）。
2. **時間軸まわり**（タイムライン形式でやる）。
3. **場面形式専用の新概念**＝`project.schema.json` の Scene に新フィールドを足すこと。

**判断が分かれるもの → 凍結側に倒す**
- **FREE 自由配置の機能拡張**：FREE は本形式の**前身**なので、強化するとタイムライン側と二重投資になる。
  ただし**タイムライン側で作った部品を FREE へ流用できる**場合は、その限りではない。
- **キーフレーム（#512 高度アニメ）**：タイムライン形式の機能として作る。場面形式側では拡張しない。

> 📌 凍結は「触らない」ではなく**「新しい編集能力を場面形式に足さない」**の意。既存 Issue の仕分けは Issue 再編で行う。

### 声と字幕の連動（利用者要望・本形式の特徴）

**音声クリップと字幕クリップを紐づけられる**＝「この字幕はこのボイスのトラックと連動する」。
ADR-0029（FREE 字幕の `subtitleSource`）で作った「字幕は対象から解決する」考え方を、
**場面内の行**ではなく**タイムライン上の音声クリップ**へ向け直したもの。具体形は未解決（下記）。

## 結果・影響

### コード

- **新設**：タイムラインプロジェクトの文書モデル（domain）・編集画面・書き出し経路。
- **共有**：1枚のフレームを描く核（`layoutScene` 系）は**両形式で共有**する＝パリティ（ADR-0001）を二重に作らない。
  違うのは「並べ方」だけ（場面の順番 vs 時刻とトラック）。**一般合成は #431（複数動画スロット・zIndex 順）で
  一部先行しているので、ゼロからではない。**
- **焼き出し**：場面形式 → タイムライン形式の変換（片道）。ADR-0030 の `freeLayoutFromPlacedContent`
  （通常→FREE の内容移送）と同じ系統の処理を、時間軸へ拡張する形になる見込み。
- **廃止**：場面形式の編集用タイムライン画面（`TimelineEditScreen`）と `timelineOverlay`。
  読み取り専用の `TimelineScreen` は残す。
- **見直し**：#329 段階(1)(3)（再生ヘッド・編集元への導線）は**タイムライン側で作り直す**。
  `playheadFrameAt` など時刻解決の純粋関数は流用できる見込み。

### 正典

- **schema**：**タイムラインプロジェクト用の新スキーマ**＝`schemas/timeline-project.schema.json`（**#627 で新設・`"1.0"`**）。
  `project.schema.json` からは `timelineOverlay` を**削除**（破壊的変更＝メジャー相当の扱いと移行方針が要る・`11 §1`）。
- **`11_SCHEMA_REFERENCE`**：新形式のフィールド表・検証ルール・自動補正を追加。
- **`CLAUDE.md`**：`§10`「本格タイムライン編集」の除外を**全面解除**へ更新。`§11` に本ADRを追記（本PR）。
  `§2-4`（テンプレ駆動・座標を触らせない）は**場面形式に限る**旨の限定が要る。
- **ADR-0018/0023**：本ADRにより**一部 Superseded**（2モデル方式は場面形式内の読み取り射影として残る）。

### α-5 の再編（利用者判断＝再定義に近い・既存 Issue は残すか一部編集して包括）

- **#329（統合タイムライン EPIC）**：本ADRの EPIC へ**再定義**。
- **吸収される見込み**：#258（SE配置）・#257（ダッキング）・#259（ノーマライズ）・#260（素材ライブラリ）・

## 未解決の論点

1. ~~**文書モデルの具体形**~~ → **決定（#627）**。`11 §7.6` 参照。**クリップ＝「FREE 要素 ＋ 時間（trackId/startSec/durationSec）」**
   ＝空間の語彙は `FreeElement`（ADR-0008）と同じものを使う（描画は `layoutScene` の FREE 分岐を共有＝パリティを二重に作らない）。
   テンプレ由来クリップは **Scene 相当を内包しない**＝`kind:'template'` のクリップが `templateId`＋差し込み口
   （`assetRefs`/`texts`/`textStyles`/`slotFits`）だけを持つ（場面という入れ子を作らない）。
   **クリップごとの `zIndex` は持たない**＝重ね順は tracks の並び順だけで決まり、そのために
   **同一トラック内で時間の重なりを禁止する**（`11 §8` V24。重ねたいならトラックを足す）。
2. ~~**スキーマの置き場**~~ → **決定（#627）**。**`timeline-project.schema.json` を新設**する（`project.schema.json` の拡張ではない）。
   版は**独立**（初期 `"1.0"`・場面形式の 1.x バンプに釣られない）＝「1つの schemaVersion で2形式」を避ける。
   **形式の判別はトップレベル `format`**＝**`"timeline"` か否かの一点**で、`projectId` の採番は両形式共通（`11 §1`・`§2.1`）。
   **場面形式のファイルは `format` を書かない**（不在＝場面形式。`project.schema` は `additionalProperties:false` ゆえ
   `format:"scene"` は検証を通らない＝CI の must-reject で固定）。`ProjectFormat` の `"scene"` は読込時の解決値
   （`resolveProjectFormat`）であって永続化しない。**この非対称は意図的**で、場面形式は本ADRで凍結されており、
   情報量ゼロのフィールド追加のために `project.schema` を版上げしないため（#627 レビュー）。
   素材・見た目設定・グループ・キーフレーム、および同梱フォント/同梱BGMの一覧は **`project.schema.json` の `$defs` を `$ref` で共有**する
   （コピーせず1か所で管理・`CLAUDE.md §2-7`）。
3. **`timelineOverlay` の削除に伴う移行**：既存プロジェクトを開いたときの断り方（`15` の状態として定義）。
   破壊的変更として project の schemaVersion をメジャーへ上げるかどうか。
4. **声と字幕の連動の具体形**（音声クリップ id を字幕クリップが参照する／グループ化する 等）。
5. **書き出しのハイブリッド境界**：どの条件でフレーム描画へ倒すか（重なり・アニメ・速度変更・クロップの有無）。
   **迷ったら全フレーム**は決定済みだが、判定条件は実装時に確定。
6. **「バラす」の意味論**：テンプレ由来クリップを分解したあと、テンプレへ戻せるか（戻せないなら `§2-5` の断りが要る）。
7. **段階の切り方**：α-5＝タイムライン編集の完成と決めたが、**範囲が広いので中の段階分けが要る**
   （文書モデル → 編集の骨格 → 書き出し → 焼き出し → 仕上げ、等）。Issue 再編で確定する。
8. **α-6 に積んでいた項目の仕分け**：タイムライン側に属するもの（#333 場面分割・#264 テキストスタイル・#265 セーフエリア・
   #266 プリセットKF→自由KF 等）は α-5 へ引き上げるか、α-6 の「追加機能」として残すか。Issue 再編で確定する。

> ✅ **決定済みへ移動**（2026-07-28）：焼き出しの単位（**全体/パート/範囲を選べる**）／場面形式の凍結範囲（**変更の種類で線引き**・上記）／
> α-5 の完了条件（**α-5＝タイムライン編集の完成**、α-6 は問題修正＋必要なら追加）。
