# ADR-0069: 書き出しの色は BT.709 にそろえて印を付ける（動画と写真の色ずれ）

- **状態**: Accepted
- **日付**: 2026-10-20
- **関連**: [`ADR-0001`](0001-rendering-parity.md)（プレビュー＝書き出し）／[`ADR-0002`](0002-ffmpeg-codec.md)・[`ADR-0013`](0013-h264-via-media-foundation.md)（エンコーダ）／[`ADR-0044`](0044-color-adjust-and-blend.md)（書き出しは FFmpeg で絵を描かない＝合成の色）／`05 §16`（書き出し）／`src-tauri/src/ffmpeg.rs`

## コンテキスト

α-8 の実機確認（2026-10-20）で、**書き出した動画の中で、写真と動画の色が合っていない**ことが分かった。
色の帯（原色・肌色・灰の段）の PNG と、それを H.264 にした動画（BT.709・色の印あり／印なし）をタイムラインに並べて書き出し、帯の中心の色を比べた（`C:\WS\stario-realcheck\color`）。

| 書き出しの区間 | BT.601 で解く（印の無い動画の FFmpeg の既定） | BT.709 で解く（HD の再生ソフトの多く） |
|---|---|---|
| 写真 | **最大差 3** | 約 25 ずれる |
| 動画（印あり） | 最大差 25 | **最大差 4** |
| 動画（印なし） | 最大差 25 | 最大差 39 |

- **1本の動画の中で色の式が混ざっている**＝写真の区間は BT.601、印のある動画の区間は BT.709 で YUV にされ、**出力には色の印が無い**。
  どちらの式で解いても、どこかがずれる（赤が 255→230、緑に赤が混ざる等）。FFmpeg 8 の色の受け渡しが、動画の区間だけ元の印を出力の変換まで運ぶため。
- **印の無い動画を BT.601 で解いている**＝HD の印なし動画は、世の中では BT.709 とみなすのが普通（プレビューもそう）。
- **プレビュー（WebView2）は正しい**＝動画の印あり・印なしとも帯の色と最大差 1。⚠️ **印の無い SD（720 未満）は BT.601（SMPTE 170M）とみなし、原色の違いまで直して表示する**（実測）。

⇒ **プレビュー＝書き出し（ADR-0001）が色で崩れている**。写真の多い動画も、再生ソフト（多くは HD を BT.709 とみなす）では写真の色がずれて見えうる。

## 判断軸

- **ADR-0001**＝プレビューで見えている色が、そのまま書き出される。
- **業界の型**＝HD の動画は **BT.709・限定範囲（tv）**で作り、**色の印を付ける**（編集ソフトの既定・投稿先の前提）。
- 書き出しの絵は FFmpeg で描かない（ADR-0044）＝**直すのは色の式と印だけ**。合成の中身は変えない。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) **出力を BT.709・限定範囲にそろえ、印を付ける。入力の動画は印に従い、印が無ければ大きさで推定（プレビューと同じ規則）** | 業界の型どおり・プレビューと一致・どの再生ソフトでも同じ色。**採る** |
| (B) 出力を BT.601 にそろえる（印は付ける） | HD で BT.601 は少数派。投稿先・再生ソフトでの扱いが割れやすい。不採用 |
| (C) 印だけ付ける（式は今のまま） | 1本の中で式が混ざっているので、印が1つでは直らない。不採用 |

## 決定

1. **出力の色は BT.709・限定範囲**。書き出しでエンコードする所（場面の静止・コマ列の共通の末尾／動画の場面／つなぎの再エンコード）は、
   映像の最後に**明示の変換**（`scale=out_color_matrix=bt709:out_range=tv,format=yuv420p`）を通す＝暗黙の変換に任せない。
2. **色の印を付ける**＝出力の項目（`-colorspace`／`-color_primaries`／`-color_trc` を bt709・`-color_range tv`）に加え、
   **H.264 の中の印（VUI）も書く**（`h264_metadata` の bsf）。⚠️ Windows のエンコーダ（Media Foundation）は出力の項目を指定しても VUI を書かない（実測）＝
   bsf が無いと、印の無い動画になる。無劣化でつなぐ所（`-c copy`）は場面ファイルの印をそのまま運ぶ。
3. **入力の動画は、プレビューと同じ規則で解く**：
   - 印がある＝その印どおり（BT.709 ならそのまま・BT.601 系〔smpte170m／bt470bg〕は原色まで BT.709 へ直す）。
   - 印が無い＝**高さ 720 以上は BT.709、未満は BT.601（SMPTE 170M）とみなす**（プレビュー〔WebView2〕の実測と同じ・業界の推定の型）。
   - BT.601 系から BT.709 へは **`zscale`**（同梱の FFmpeg に入っている zimg）で原色ごと直す。⚠️ `colorspace` フィルタは実測でプレビューと最大 33 ずれた／`zscale` は最大 11。
   - それ以外の印（BT.2020・HDR など）は今までどおり（FFmpeg の既定の扱い）＝別の話として残す。
4. どの印かは、書き出しの前に元の動画を調べて決める（今も音の有無を調べている所と同じ）。決め方は純粋関数（調べた文字列 → 前処理のフィルタ）にして検査する。

## 結果・影響

- **既存の動画を書き出し直すと、動画の区間の色が変わる**（直った側＝プレビューに近づく）。データは書き換えない＝移行は無い。
- 写真・文字の区間は、BT.709 の印つきになる＝印を読む再生ソフトでは見た目は変わらない（式と印がそろう）。
- 書き出しの引数の検査（`ffmpeg.rs` の tests）は、末尾の変換と印の項目を含む並びに改める。
- 同梱物は変わらない（zimg は既に FFmpeg に組み込まれている）。`13` の同梱物の一覧は変えない。
- 正典（`schemas`／`11`）は変えない。

## 未解決の論点

- BT.2020・HDR の動画（iPhone の HDR 撮影など）を SDR の BT.709 へ落とす扱い（トーンマッピング）は別の ADR。今は FFmpeg の既定のまま（明るさ・色が変わりうる）。
- 印の無い SD をプレビューと同じに直す精度（`zscale` で最大 11）。これ以上そろえるにはブラウザの色管理と同じ計算が要る。
