# ADR-0070: 書き出しのコマを、隠した別の窓でも描いて並べて速くする（タイムライン形式）

- **状態**: Accepted
- **日付**: 2026-10-23
- **関連**: [`ADR-0001`](0001-rendering-parity.md)（プレビュー＝書き出し＝描画核は1つ）／[`ADR-0007`](0007-detailed-edit-mode.md)（書き出しの経路は1つ）／[`ADR-0032`](0032-timeline-project-format.md) 決定22（タイムライン形式の書き出し＝全コマを描く）／[`ADR-0050`](0050-preview-popout-window.md)（別の窓＝状態の持ち主は本体ひとつ）／`11_TIMELINE_REFERENCE §7.6.4`（書き出しの組み立て）／#1203（区間ごとの書き出し）・#1517・#1522（書き出しの高速化）

## コンテキスト

タイムライン形式の書き出しは、**全部のコマを画面（WebView）で描いて PNG にし**、FFmpeg がつないで動画にする（ADR-0032 決定22）。
描くのは**プレビューと同じ関数**（`layoutTimelineAt`→`layoutToSvg`）で、SVG を `<img>` に読ませて canvas に焼く（ADR-0001）。

2026-10-22〜23 に、絵を変えないまま速くできるところを詰めた。

- #1517：前のコマと同じ絵は描かずに写す。描き直し・PNG 化・運ぶのを重ねる。
- #1522：PNG 化を Web Worker へ移す。バイトのまま運ぶ。同じ絵の写しをまとめる。大きな data URL の Blob を使い回す。

結果、develop と交互に測って講座の動画（3分36秒）は 805→407 秒になった。出来上がる動画は md5 で一致している。

**残る重さは「SVG を読んで描く」1か所**で、これは画面の**主スレッド**でしか動かない。

- 1コマの SVG は約 6MB で、その大半が立ち絵・背景の data URL（実測）。
- SVG を絵にするには文書（`<img>`）が要る。Worker の `createImageBitmap(Blob)` では SVG を解けない＝Worker では代われない。
- 主スレッドを増やす方法は、**描画プロセス（窓）を増やす**ことしかない。

**2窓の試作**（2026-10-23・`C:\WS\stario-realcheck\par`）。この PC は最低検証機（Core Ultra 5 125U・16GB）。
起動中のアプリに窓を足し、同じ重さの絵（1920×1080・背景＋立ち絵2枚＋字幕）を同時に描かせた。

| | 合計で描けた枚数（毎秒） | 1窓に対して | 窓1つあたりの1コマ |
|---|---|---|---|
| 1窓 | 14.9〜15.6 | 1.0 倍 | 64〜67 ms |
| 2窓 | 25.4〜26.1 | **約 1.68 倍** | 70〜76 ms |
| 3窓 | 31.2〜31.3 | **約 2.06 倍** | 80〜95 ms |

試作で分かったこと：

- **窓ごとに別の描画プロセス**になった。WebView2 は「共有されうる」としか書いていないので、確かめる必要があった。
- **画素はすべての窓・すべての回で同じ**だった（全画素のハッシュ）。
- **隠した窓**（`visible:false`）も `visibilityState` は visible のままで、遅くならず、画素も同じだった。
- 足した描画プロセスは、待機で約 53MB。

講座で見積もると、407 秒（うち FFmpeg 約 60 秒・コマ約 345 秒）が、2窓で約 265 秒、3窓で約 227 秒になる。

## 判断軸

1. **出来上がる動画を変えない**（ADR-0001・ADR-0026③）＝速さのために絵・音・コマの数を1つも変えない。確かめ方は**今の書き出しと md5 一致**。
2. **書き出しの経路は1つ**（ADR-0007）＝新しい書き出しの道を作らない。描くのは同じ関数、FFmpeg への渡し方も同じ。
3. **黙って違う動画を出さない**（ADR-0026④）＝窓が落ちた・遅れた・コマが抜けた、を「成功」として出さない。
4. **最低検証機で効く**＝この PC で効かないものは採らない（2窓で 1.3 倍未満なら見送る、と事前に決めていた）。
5. **利用者に操作を増やさない**（§2-3）＝窓が増えたことは見せない・選ばせない。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) **隠した窓でコマを描き、本体と並べる**（区間の中のコマの範囲を窓に分け、**同じ置き場**へ置く） | 試作で 1.68〜2.06 倍・画素同じ。描く関数は同じ・FFmpeg への渡し方も同じ（1本のコマ列）。**採用** |
| (B) 区間（#1203）ごとに窓へ割り振る | 講座は区間が1つ（`encode 1 clips`）＝並ばない。区間を細かく割ると圧縮が別々になり、動画のバイトが変わる（md5 で確かめられない）。不採用 |
| (C) Worker で描く（OffscreenCanvas） | SVG を Worker で絵にできない。不採用 |
| (D) 動かない部分を層に分けて使い回す | 重ね方の丸めで画素が ±1 ずれうる＝md5 で比べられない・判断軸1に反する。不採用 |
| (E) 描画と FFmpeg の圧縮を重ねる（区間ごと） | 窓を増やさず効くが、講座は区間が1つで重ならない。圧縮を割るとバイトが変わる。**今回は採らない**（A と独立に後で検討） |
| (F) 何もしない | 最低検証機で講座 407 秒・11分の動画で 20 分を超える見込み。不採用 |

## 決定

1. **タイムライン形式の書き出しで、コマを描く仕事を「隠した別の窓」にも分ける**（選択肢 A）。
   描く関数は本体と同じもの（`buildTimelineFrames`）＝窓は同じアプリの同じ画面のコードを読む。
2. **分ける単位は「区間の中のコマの範囲」**。区間（#1203）ごとの置き場（`framesDirForSegment`）は1つのまま、そのコマの番号の範囲を窓に分け、**同じ置き場に正しい番号で置く**。
   FFmpeg に渡すのは今と同じ1本のコマ列＝圧縮は1回＝動画のバイトは変わらない。
   - 範囲の頭のコマは、窓ごとに描く（前の窓の最後のコマから写さない）。同じ SVG からは同じ絵になる。
   - **動画の部品のコマ**（`videoFramesDirOf`）は、窓どうしが同じ置き場を取り合わないよう、**本体が先に1回だけ焼き出す**（窓は読むだけ）。
3. **状態の持ち主は本体の窓ひとつ**（ADR-0050 と同じ）。描く窓は本体から「始めた時点の文書」と担当の範囲を受け取り、描いて置き、進み具合を返すだけ。保存・音・書き出しの締め（ロック）・FFmpeg は本体だけ。
4. **窓の数は自動で決める**（利用者に選ばせない）。
   - 足す窓は**最大2つ**（合計3窓）。
   - 論理コアの数と空きメモリで決める（`extraRenderWindows`）：論理コア 8 以上で2つ・4〜7で1つ・それ未満は足さない。
     空きは **1GB を残して、窓1つあたり 600MB**（実測＝描く窓の描画プロセスが最大約 470MB、窓で分け合う GPU の処理が窓1つあたり約 250MB）。
   - ⚠️ 残す空きを当初 2GB にしたところ、最低検証機（16GB）で普段使いのアプリが開いていると空きが 2.2GB 前後で、**窓が1つも足せなかった**（実測）。
5. **短い区間では使わない**。毎コマ描く区間が `PARALLEL_MIN_FRAMES`（300コマ＝30fps で10秒）に満たなければ1窓で描く。窓を立てる数秒で得が消えるため。
   区間は `PARALLEL_CHUNK_FRAMES`（240コマ）ずつに小分けにし、空いた描き手から取っていく（絵の重さは場所で偏る＝等分すると重い所を引いた窓だけが遅れる）。
6. **窓は隠す**（`visible:false`・タスクバーに出さない）。試作で、隠しても遅くならず画素も同じだった。
   ⚠️ WebView2 の版で振る舞いが変わりうるので、書き出しの前に**1コマ描いて本体と画素を比べ、違えば窓を使わない**（下の決定7と同じ扱い）。
7. **窓が落ちた・応答しない・違う絵になったら、その窓の残りを本体が描き直して続ける**（1窓へ戻す）。
   応答しないとみなすのは 30 秒（窓は 24 コマごとに知らせる）。窓が引けない素材・受け取っていない見た目パターンを引いたら、窓はその範囲を失敗にする（黙って違う絵にしない）。
   - **コマが抜けた動画を出さない**＝FFmpeg に渡す前に、置き場のコマの数と番号が全部そろっているかを Rust で確かめる。足りなければ断る（`image2` は抜けた番号で黙って止まるため）。
   - 中止は全部の窓へ伝え、窓は描いている途中のコマを置き終えて止まる。
8. **受け入れ条件**：同じ動画を、窓を使わない書き出しと窓を使う書き出しで出し、**md5 が一致**すること。講座・機能盛り（動画の部品・喋っている間の動き）・縦の動画で確かめる。
9. **場面形式は対象外**（ADR-0032＝凍結）。

## 結果・影響

- **コード**：
  - `renderer/export/buildTimelineFrames.ts`＝置き場の中の番号のずらし（範囲の頭が置き場の 0 番ではない）。
  - `renderer/export/buildTimelineParts.ts`＝範囲を窓へ分ける。
  - 描く窓の入口（窓が受ける命令・返す進み具合）、本体の振り分けと戻し方。
  - Rust：置き場のコマがそろっているかの確かめ。
  - 窓の作成の権限（`capabilities`）＝描く窓だけの小さな権限を足す。
- **正典**：
  - `11_TIMELINE_REFERENCE §7.6.4` に「コマは複数の窓で描くことがある（出来上がりは同じ）」を追記する（実装の PR で）。
  - schema は変えない（文書の形は同じ＝`schemaVersion` も変わらない）。
- **利用者**：画面は変わらない。書き出しが速くなるだけ。メモリは書き出しの間だけ窓1つにつき数百 MB 増える。
- **検査**：分け方と番号は純粋関数にして検査する。窓そのものは自動の検査では通らないので、実機で md5 を比べる（PR 本文に記録）。

## 実装後の実測（2026-10-23・最低検証機・develop の exe と同じ時間帯に交互に書き出し）

| 動画 | develop | この方式（窓を2つ足す） | 出来上がり |
|---|---|---|---|
| 講座（3分36秒・6491コマ） | 586・401 秒 | **394・301 秒**（−25〜33%） | md5 すべて一致 |
| 機能盛り（20秒・動画の部品＋喋っている間の動き） | 44・44・42 秒 | **33・35・32 秒**（約 −24%） | md5 すべて一致 |
| 場面形式（自由配置＋動き） | — | 変わらない（窓を使わない） | md5 一致 |

- 試作の「描く速さ 2.06倍」より伸びが小さいのは、FFmpeg の圧縮・動画の部品の焼き出し・窓の立ち上げが並ばないため。
- **描く窓の描画プロセスを書き出しの途中で落としても**、本体がその範囲を描き直し、md5 は一致した（その間、進み具合が止まって見える＝応答待ちを 30 秒にした）。

## 未解決の論点

- ~~窓の数・最短の長さ・空きメモリのしきい値~~ → 決定4・5 に書いた（実測から）。
- ~~素材の絵を本体から受け取るか~~ → **窓が自分で読む**（本体と同じ関数＝同じ文字列）。見た目パターンの既定素材だけは使う分を受け取る。本体が引けて窓が引けない素材は失敗にする。
- ~~字体の読み込み~~ → パックの字体の置き場を受け取り（`setPackFontSources`）、同じ `loadExportFonts` を通す。違えば確かめの1コマで外れる。
- 中止を押したときの窓の閉じ方は自動の検査のみ（実機の手での確かめは未）。
- 将来、選択肢 E（描画と圧縮を重ねる）を足すか。
