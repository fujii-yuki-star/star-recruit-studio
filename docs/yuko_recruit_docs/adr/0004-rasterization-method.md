# ADR-0004: 本番ラスタライズ手段の単一化（静止レイヤーのSVG→PNG）

- **状態**: Accepted（2026-06-12 承認）
- **日付**: 2026-06-12
- **関連**: [`0001-rendering-parity.md`](0001-rendering-parity.md)（方式A2ハイブリッド／残課題①）・`05_RENDERING_SPEC.md §2.5,§3.1`・スパイク `scripts/adr0001-spike.ts`・`CLAUDE.md §3`

---

## コンテキスト

ADR-0001 で描画方式 **A2ハイブリッド**（静止レイヤーをプレビューと同一のWeb描画でPNG化し、FFmpegは動画スロット合成・トランジション・音声・尺・結合・エンコードに限定）を採択した。スパイク（`scripts/adr0001-spike.ts`）で「**同一SVG＋同一ラスタライザ＝byte-identical**」を実証し、描画の中間表現を **SVG** に確定した。

しかし ADR-0001 の残課題①「**本番のラスタライズ手段を単一化**（resvg案 / WebView canvas案）」が未決定のまま残っている。これを決めないと `renderer/export` の本実装に着手できない。

決め直す必要が生じた決定的な事情：

- **製品は Tauri**＝「**WebViewフロント（ブラウザエンジン＝Blink/WebView2、Nodeランタイムなし）＋Rustバックエンド**」。
- スパイクは **Node の `@resvg/resvg-js`** でPNG化したが、これは**製品アプリ内では動かない**（Node専用ネイティブaddon）。スパイクはあくまで検証用であり、製品の描画経路ではない。
- プレビューは既に **WebView上でSVGをDOM表示**している（`renderer/sceneSvg.ts` → `app/components/ScenePreview.tsx`）。

すなわち「製品で静止レイヤーをどうPNG化するか」を、Tauriの実行環境を前提に1つに確定する。

---

## 決定の判断軸

1. **パリティ最優先**：プレビュー＝出力の一致。特に日本語テキストを描く**描画エンジンの同一性**（ADR-0001の生命線）。
2. **Tauri実行環境との適合**：WebViewフロント／Rustバックエンドのどちらで動くか、追加ランタイム同梱の要否。
3. **実装・保守の容易さ／依存の重さ**。
4. **グラボ無し業務PCでの速度**（長尺・最大80シーン規模、`01 §15.2`）。
5. **フォント・色空間の一貫性**。

---

## 検討した選択肢

### 選択肢A: WebView Canvas（プレビューと同一エンジンでラスタライズ）【推奨】

プレビュー表示に使うのと**同一のSVG**を、オフスクリーンの `<canvas>` へ描画してPNG化する。`new Image()` にSVG（data URL / Blob）を読ませ `drawImage` → `canvas.toBlob('image/png')`。描画は純フロント（WebView＝Blink）で完結し、得たPNGバイト列はTauriコマンドでファイル保存、またはFFmpegへ渡す。

- **利点**
  - プレビューと**完全に同一のWebエンジン**でテキスト・フォント・半透明・角丸・zIndex合成を描く＝**パリティを構造的に保証**（ADR-0001 の狙いに最も忠実）。
  - 追加のネイティブ依存が不要（resvgクレートのビルド・クロスコンパイル・配布が要らない）。
  - 「描く場所が常にWebViewの1つ」になり、preview/export間のエンジン差が原理的に消える。
- **欠点**
  - **フォントのロード完了待ち**（`document.fonts.ready`）等のタイミング制御が要る（ADR-0001 未解決②）。
  - SVG内の**外部画像参照はcanvas汚染（tainted）**で `toBlob` 不可 → **素材画像はdata URLでSVGにインライン**化が必要（または同一オリジン化）。
  - WebView2のバージョン差で極僅かな描画差が出る可能性（配布時のWebView2運用で吸収）。
  - 大量シーンをメインスレッドでPNG化するとUIブロック → OffscreenCanvas＋Worker／逐次処理で緩和。

### 選択肢B: Rust resvg クレート（バックエンドでラスタライズ）

同一SVG文字列を Rust 側（Tauriコマンド）の `resvg`/`usvg`/`tiny-skia` でPNG化する。

- **利点**：ヘッドレス・高速・決定論的。スパイクの `resvg-js` と同系エンジン。メインスレッドを汚さない。
- **欠点**
  - **プレビュー（Blink）と別のラスタライザ** → 日本語フォントのヒンティング／アンチエイリアスがWebViewと微妙に異なりうる＝**パリティの一番の懸念**。これは ADR-0001 が選択肢B（FFmpegで全描画）を退けたのと**同種のリスク**を再び抱え込む。
  - フォントを resvg に別途ロード／指定し、WebViewと同一フォント・同一設定を担保する手間。
  - Rust依存の追加とビルド。

### 選択肢C: resvg-js を Node サイドカーとして同梱

スパイクのまま `resvg-js` を動かす Node を別プロセスで Tauri に同梱する。

- **欠点**：Nodeランタイム同梱で配布が重く複雑、Tauriの利点を損なう。プレビューとも別エンジンでパリティ面の利点もない。→ **不採用**。

## 決定

> **選択肢A（WebView Canvas）を採用する（Accepted, 2026-06-12）。** すなわち、**`renderer` が生成する同一SVGを、プレビューはDOM表示・出力はオフスクリーンcanvasでPNG化し、ともにWebView（Blink）の同一描画エンジンで描く。**

理由：本製品の生命線である**パリティ**を、プレビューと**同一エンジンで描く**ことにより構造的に保証できる。Bは速度で勝るが、ADR-0001 がまさに退けた「プレビューと別エンジンによるパリティ差（特に日本語フォント）」を再導入し、本プロジェクト最大のリスクと正面衝突する。スパイクの `resvg-js` は **Node検証用**であって製品経路ではないと明確に位置づける。

### 実装の要点

- `renderer/layout.ts`＋`sceneSvg.ts` が吐く**同一SVG**を preview（DOM）／export（canvas→PNG）双方で使う。
- 素材画像（写真／ロゴ／ゆうこ）は **data URL でSVGにインライン**してcanvas汚染を回避（ファイル→base64 はTauriコマンドで供給。横断タスク「実画像をSVGスロットへ」と連動）。
- ラスタライズ前に `document.fonts.ready` を待つ。同梱OFLフォントを CSS/SVG で**同一指定**。
- PNGバイト列はフロントで生成し、**Tauriコマンド（Rust）はファイル保存とFFmpeg(sidecar)受け渡しのみ**（描画はしない＝ADR-0001のFFmpeg責務限定と一致）。
- 長尺はシーン単位で逐次PNG化（`05 §16`）。必要に応じ OffscreenCanvas＋Worker。

## 結果・影響

- `renderer/export` は **WebView上のラスタライズユーティリティ**（`svg文字列 → PNG Blob/Uint8Array`）として実装し、`renderer/preview` とSVG生成ロジックを共有する。
- Tauri側コマンドは「PNG（バイト列）を受けてプロジェクトの一時フォルダへ保存」「FFmpeg合成を起動」を担当。**描画責務は持たない**。
- 素材は早期に「**ファイル → data URL**」経路が必要（`<image href="data:...">`）。これは「実画像をSVGスロットへ表示」と同じ依存であり、まとめて整備する。
- **ADR-0001 残課題①（ラスタライズ手段の単一化）をクローズ**。残②（テキスト折返しのフォント実測化）・残③（動画ありシーンの overlay 実機確認）・残④（色空間/ガンマ・長尺性能）は引き続き未解決。
- `05_RENDERING_SPEC.md §3.1`（高速プレビュー実装候補）に「**WebView Canvasでのラスタライズ＝出力と共有**」を追記推奨。
- **ADR-0002（FFmpeg/コーデック）との関係は不変**：FFmpegは PNG／動画／音声の合成のみ。

---

## 未解決の論点

1. **フォントロード完了の確実な待機**：同梱フォントの `FontFace` ／ `document.fonts.ready` の取り扱い、ロード前ラスタライズの防止。
2. **WebView2バージョン固定の配布運用**：描画再現性の担保（同一バイナリ前提）。
3. **data URL インライン時のメモリ**：大画像×多シーンでの消費 → 逐次生成・解放方針。
4. **色空間／ガンマ**：PNG overlay と動画スロットの色差（ADR-0001 未解決③と同件）。
5. **性能実測**：グラボ無しPC・長尺での `canvas.toBlob` 所要時間（ADR-0001 未解決④）。
