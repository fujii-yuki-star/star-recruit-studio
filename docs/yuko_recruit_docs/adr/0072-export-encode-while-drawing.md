# ADR-0072: 書き出しの圧縮を、コマを描きながら進める（タイムライン形式）

- **状態**: Rejected（試作して測った結果、採らない・利用者判断 2026-11-05）
- **日付**: 2026-11-04
- **関連**: [ADR-0070](0070-export-parallel-render-windows.md)（隠した別の窓で描く）／[ADR-0001](0001-rendering-parity.md)（描画核は1つ）／[ADR-0007](0007-detailed-edit-mode.md)（書き出しの経路は1つ）／[ADR-0071](0071-voice-engine-on-demand.md)

## コンテキスト

タイムライン形式の書き出しは「①コマを全部描いて置き場へ置く → ②FFmpeg が置き場の連番を読んで圧縮する → ③音を混ぜる」を**順番に**行っていた。
②は①が全部終わるまで始まらない。記録では、講座の動画（約 380〜420 秒）のうち圧縮が約 44 秒、11 分の動画（約 1,226 秒）のうち約 144 秒だった。

利用者判断（2026-11-04）で、「描けたコマを番号順に FFmpeg へ流し込む」案（A）を採る。小分けごとに圧縮してつなぐ案（B）は、つなぎ目で出来上がりのバイトが変わり、これまでの合格の基準（md5 一致）が使えなくなるため採らない。

## 判断軸

- **出来上がりは1バイトも変えない**（md5 一致を合格の基準のまま保つ）。
- 描く側（本体・隠した窓＝ADR-0070）の仕組みは変えない。
- 中止・失敗・窓が落ちたときに、FFmpeg を取り残さない・黙って欠けた動画を出さない。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) 描けたコマを番号順に FFmpeg の標準入力へ流す（`image2pipe`） | 圧縮する中身と順序は今と同じ。実 FFmpeg（h264_mf）で連番ファイル入力と md5 が一致することを確かめた（2026-11-04・300 コマ＋音）。**採用** |
| (B) 小分けごとに圧縮して最後につなぐ | 並べ直しは要らないが、つなぎ目で出来上がりが変わる（md5 一致を捨てることになる）。 |
| (C) 今のまま | 圧縮の時間（全体の約1割）がそのまま残る。 |

## 決定

**採らない。** 試作（下の「試作した形」）は出来上がりが1バイトも変わらないところまで作れたが、
いつも使う環境（省電力型のノート PC）では速くならなかった（下の「測った結果」）。
得られるものが誤差の範囲なのに、書き出しの仕組みに「コマを待って流す」「失敗したら両方止める」という込み入った部分が増えるので、取り込まない。
試作は枝 `feat/export-encode-while-drawing`（コミット `bc035f14`・`a33cef52`）に残す＝develop には入れない。

## 測った結果（2026-11-05・講座の動画 3分36秒・Core Ultra 5 125U／14 スレッド／15.5GB）

| 回 | 今の版（develop `f4d35134`） | 試作（描きながら圧縮） |
|---|---|---|
| 1 | 400 秒 | 396 秒 |
| 2 | 392 秒 | 383 秒 |
| 3（使用率も記録） | 357 秒 | 355 秒 |

- 出来上がりは全部の回で md5 一致（`bb291886…`）＝流し込みは正しく動いた。
- 3回目の記録：今の版は描き終えた後に**約 55 秒**（圧縮＋音を混ぜる）待つ。試作はそれが**約 25 秒**に縮んだが、**描いている時間がほぼ同じだけ延びた**。
- 描いている間の CPU 使用率は 50〜60%（余っているように見える）。この CPU は**省電力型（15W 級）で電力の上限で頭打ち**になるので、圧縮を同時に走らせると描く側の速さがそのぶん落ちる＝取り合いになる、と見ている。

## 戻す条件

- 電力や冷却に余裕のある PC（デスクトップ等）で使う人が増え、そちらで測って**1割前後**速くなると確かめられたとき。そのときは試作の枝から取り出し、条件（CPU の種類・窓の数）で切り替える形を考える。

## 試作した形（参考）

1. **書き出しを頼むのを、描き始める前にする。** 区間の割り方（どの区間を描くか・実動画のまま流すか）を先に全部決め、FFmpeg への依頼（`export_video`）をすぐ出す。そのあとで描く。
2. **描いたコマは置き場へ置くまでは今と同じ。** Rust は、置き場へ**書き終えた**コマの番号を覚える（`stage_export_frame`／`stage_export_frame_png`／`copy_export_frames`）。
3. **FFmpeg へは番号順に流す。** 区間ごとに、0 番から「置くはずのコマの数」まで、**そのコマが置かれるのを待って**から読み、標準入力へ書く。隠した窓が番号を飛ばして描いても、流す順は崩れない。
4. **一度置いたコマは書き直さない。** 同じ絵は同じバイトになる（ADR-0070）ので、窓が落ちて範囲を描き直すときも、置き終えたコマは飛ばす（流している最中のファイルを書き換えない）。
5. **描き終えたら知らせる**（`finish_export_frames`）。知らせた後に足りないコマがあれば、待ち続けずに失敗として返す（黙って短い動画を出さない＝今の「抜けを確かめる」と同じ断り）。
6. **描くのに失敗した・中止した**ときは、書き出しの中止（`cancel_export`）で FFmpeg も止める。**圧縮が先に失敗した**ときは、描くのを止めてそちらの断りを出す。
7. **進み具合のバーは、描いている間は描いた数で進める**（圧縮の知らせで段が飛ばない）。描き終えた後の残りは圧縮の知らせで進める。
8. **場面形式の書き出しは変えない**（流し込みは、頼むときに印を付けた区間だけ）。

## 結果・影響

- 採らないので、コード・正典（schemas/11/12）は変わらない。書き出しは今までどおり「描き終えてから圧縮する」。
- 試作で FFmpeg が描いている間ずっと動くと、そのぶんメモリを使う時間も延びる（採らない理由の補足）。
- 試作で触ったコード（枝の中だけ）：`src-tauri/src/ffmpeg.rs`（置いたコマの記録・待って流す・`finish_export_frames`）／`src/renderer/export/buildTimelineParts.ts`（割り方を先に決める・描く、を分ける）／`src/app/store/timelineStore.ts`（頼んでから描く）／`src/infrastructure/ffmpegExport.ts`。

## 未解決の論点

- 電力に余裕のある PC で実際にどれだけ速くなるかは測っていない（戻す条件の判断材料）。
