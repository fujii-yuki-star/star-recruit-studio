# ADR-0076: 「採用動画」を拡張パックの鍵で出す（本体の入口を一般向けにする）

- **状態**: Accepted（2026-11-26・利用者判断＝B 案・3点ともおすすめどおり。**実装はメンバーへの説明のあと**）
- **日付**: 2026-11-26
- **関連**: ADR-0011（動画の種類 `videoKind`）／ADR-0043（α と β の線引き＝追補で「β は拡張パックで足す外付け」）／ADR-0060（拡張パック・組み込み機能の鍵）／ADR-0061（あなた向け会社説明＝最初の鍵）／ADR-0026（挙動一致・④壊れて見える仕様を警告で済ませない）／ADR-0024（自己完結）／`CLAUDE.md §1`・`§2-3`・`§2-7`／`11 §3.1`／`06`（画面一覧の「作成ウィザード」）／`12`（AI の依頼の作り）

## コンテキスト

利用者の指摘（2026-11-26）：「新しい動画を作る」の流れだけ、**露骨に採用の道具に見える**。β（採用の関係者向け）は拡張パックで足す外付けとして作ってあるのに、入口がそれと合っていない。

ADR-0043 の追補で「β は会社・採用に固有の機能ではなく、**拡張パック（ADR-0060）で足す外付け**」と改めた。あなた向け会社説明（ADR-0061）はそのとおり鍵（`personalized-briefing`）で出している。
ところが「採用動画」（`videoKind=recruit`）は ADR-0011 のまま本体に入っていて、しかも本体の既定になっている。調べた事実は次のとおり。

| 場所 | いま | 見え方 |
|---|---|---|
| 作成ウィザードの最初の段（`WizardScreen.tsx`） | 種類の1枚目が「採用動画」で、**最初から選ばれている**（`initialMeta.videoKind ?? VIDEO_KIND.recruit`）。目的も採用の7つが出る | 最初の画面が採用の道具 |
| 新しい動画の土台（`projectStore.ts` の `defaultHeader`） | `purpose: "new_graduate"`＋空の `companyInfo`。**白紙から作った動画も、中身は「採用動画・新卒採用」** | 見えないが、保存した文書は採用になる |
| 保存の組み立て（`persistence.ts` の `assembleProject`） | 種類が無ければ `recruit` を書く | 同上 |
| 案内の文 | 「求職者に伝えたい魅力を…」（ゆうこの助言）・写真の段の「会社の写真や動画を…」（一般でも出る）・ホームの「会社情報と素材を入れて…」（`uiLabels.ts` の `idle`）・使い方の「採用動画と一般動画から選びます」（`helpGuide.ts`） | 一般を選んだ人にも採用の言葉が出る |

見た目パターンは汎用の種類（`template.schema.json` の `category`）だけで、採用専用のものは無い。

## 判断軸

- **本体は一般向け**（ADR-0043）。採用の関係者でない人に、採用の道具に見せない。
- **作ったものを閉じ込めない**（ADR-0026・ADR-0024）。鍵が無くなっても、採用で作った動画は開けて直せる。
- **鍵は1つの仕組み**（ADR-0060）。採用動画のために別の出し分けの道を作らない。
- **正典の形（schema）は変えない**。データの互換を崩さない。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) 入口を一般向けに倒すだけ（既定を一般にする・文を中立にする・採用は残す） | 小さい。ただし鍵の無い人にも「採用動画」が見え続け、β の線引き（ADR-0043 追補）と合わない。**単独では採らない**（下の決定に含まれる） |
| (B) **「採用動画」を拡張パックの鍵で出す** | 線引きと一致する。既存の採用動画の扱い・新しい動画の土台を決める必要がある。**採用** |
| (C) 採用の機能をパックへ外出しする（依頼の作りや目的をデータで運ぶ） | ADR-0060 決定1（パックにプログラムを入れない・機能はアプリに組み込み済み）に反する。不採用 |

## 決定

### 決定1：新しい鍵 `recruit-video` を作り、β のパックに同梱する

- 組み込み機能の鍵に **`recruit-video`**（画面名「採用動画」）を足す（`KNOWN_PACK_FEATURES`・`PACK_FEATURE`・`uiLabels` の機能名）。
- **あなた向け会社説明（`personalized-briefing`）とは別の鍵**にする。配るときは同じ β のパックに両方を入れる（利用者判断 2026-11-26）。将来、採用動画だけのパックも作れる。
- 採用の機能そのもの（会社情報の欄・採用の目的・同梱の AI への採用向けの依頼）は**アプリに組み込んだまま**（ADR-0060 決定1）。鍵は**見せるかどうか**だけを決める。

### 決定2：鍵が無いと、「新しく採用動画を作る」入口を出さない

- 作成ウィザードの「どんな動画を作りますか？」に「採用動画」のカードを出す条件：
  **鍵 `recruit-video` がある** または **開いている動画の保存済みの種類が採用**（決定3）。
- 出さないときは、種類の選択そのものを出さない（選択肢が1つしかない選択は置かない）。目的は一般の4つだけを出す。
- 使い方（`helpGuide.ts`）・ホームの案内（`idle`）など、**種類の選択に触れる文も同じ条件で書き分ける**。鍵が無ければ採用に触れない。

### 決定3：鍵が無いパソコンでも、以前に作った採用動画はふつうに開いて直せる

- 開く・場面の編集・書き出し・**会社情報の見直し（ウィザード）**・複製は、鍵の有無に関わらずできる（利用者判断 2026-11-26）。
- ウィザードを開いたとき、その動画の保存済みの種類が採用なら「採用動画」のカードを出し、選んだ状態で開く（決定2 の条件）。一般へ切り替えることもできる。ウィザードを出るまではカードを出したままにする（切り替えて戻せる）。
- 鍵が外れたことを理由に、**黙って種類を書き換えない・会社情報を消さない**（ADR-0026④）。
- 動画の一覧は今のまま（種類で隠さない）。

### 決定4：新しい動画の土台は「一般動画」にする

- `defaultHeader`（新しい動画・白紙から作る動画の土台）を **`videoKind: general`**、目的は**一般の目的の先頭**（`GENERAL_PURPOSES[0]`＝ウィザードで種類を切り替えたときに寄せる先と同じ）、**空の `generalBrief`**（`title: ""`）にする。空の `companyInfo` は持たない。
  - 作りかけの文書が空の題で保存されるのは、いまの空の会社名と同じ扱い（読み込みで弾くのは構造の破損だけ＝`persistence.ts`・#416）。
- 保存の組み立て（`assembleProject`）で種類が無いときは**中身から決める**＝会社情報だけを持つなら `recruit`、それ以外は `general`（実装時に精緻化 2026-11-27：一律に `general` と書くと、会社情報だけを持つ文書が schema の排他〔一般は `generalBrief` 必須〕に落ちて保存できなくなるため）。
- ⚠️ **読み込みの移行（`migrateProject`）は `recruit` のまま**。`videoKind` の無い古い文書（1.0）は採用専用時代のものなので、採用として読む（`11 §3.1` の「省略時は `recruit`」＝**読み込みの互換の規則**として残す）。

### 決定5：鍵があるときも、一般が先で最初から選ばれている

- 鍵があるときの並びは「一般動画・社内発表」→「採用動画」。新しい動画では一般が選ばれた状態で始まる（利用者判断 2026-11-26）。
- 既存の採用動画をウィザードで開き直したときは、その動画の種類（採用）が選ばれている（決定3）。

### 決定6：案内の文を種類で書き分ける（採用の言葉は採用を選んだときだけ）

- ゆうこの助言・写真の段の説明など、ウィザードの中の文は**種類ごとに持つ**。一般で採用の言葉（求職者・会社の写真）を出さない。
- 種類に関わらない文（ホームの案内など）は、会社にも発表にも寄らない言い方にする（例：「伝えたいことと素材を入れて」）。
- ⚠️ 「会社の見た目」（ADR-0036）はこの ADR では変えない。社内の発表でも会社の色・ロゴは使うので、採用に固有の言葉ではない（下の未解決の論点）。

## 結果・影響

### 正典（この ADR と同じ PR で直す）

- `CLAUDE.md §1`（プロダクト一行＝採用動画は拡張パックで出す）・`§11`（1行）
- `adr/README.md`（一覧に1行）
- ADR-0011・ADR-0043・ADR-0060 に追補（どこが改まったかを指す）
- `11 §3.1`（「省略時 `recruit`」は読み込みの互換の規則で、新しい動画の既定は一般）
- `06`（作成ウィザードの段の説明・鍵で出す画面の一覧）
- `01`（製品の説明）・`16`（用語＝動画の種類）

### schema

- **変えない**。`videoKind` の enum も `if/then/else` も今のまま。`schemaVersion` も据え置き。
- 拡張パックの `features` は形（`pattern`）なので、鍵を足しても schema は変わらない（アプリ側の `KNOWN_PACK_FEATURES` に足す）。

### 実装（メンバーへの説明のあと・1つの PR で）

1. 鍵 `recruit-video` を足す（`extensionPack.ts`・`uiLabels.ts` の機能名・試験用パックを作る道具 `make-starpack.mjs` の例）。
2. ウィザード：決定2・3・5・6（カードの出し分け・既定・文の書き分け）。
3. 土台：決定4（`defaultHeader`・`assembleProject`）。⚠️ 新しい動画が採用になっている前提の検査があれば直す（`persistence.test.ts` の「既定 recruit」は**読み込みの移行**の検査なので残す）。
4. 使い方・ホームの案内（決定2・6）。
5. 検査：鍵なしで採用のカードが出ない／鍵ありで2枚・一般が選ばれている／鍵なしで既存の採用動画をウィザードで開くと採用が選ばれている・会社情報が残る／白紙から作って保存すると一般になる／一般で採用の言葉が出ない（**画面まるごと**で採用の言葉を探す検査＝`CLAUDE.md §7`）。変異チェックを回す。
- 同梱の AI の採用向けの依頼（`localVideoPlanProvider.ts`・`buildVideoPlanRequest.ts`）は**変えない**（鍵があれば今までどおり使う）。`12` も変えない。
- あなた向け会社説明（ADR-0061）は採用で作った動画を材料にすることが多いが、鍵が別なので**影響しない**（登録できる動画を種類で絞っていない）。

## 未解決の論点

- 「会社の見た目」の名前（ブランドの色・ロゴ・文字の形）。一般向けに見せるなら名前を変える案もある（利用者確認）。
- 鍵を持つ人に向けた「採用動画を作る」近道（ホームに出すかどうか）。まずはウィザードの2枚目のカードだけで始める。
- 試験用・サンプルの動画案（`sampleVideoPlan.ts`＝目的が新卒採用）を一般にそろえるか。利用者の目に触れる経路が無ければそのまま。
