# ADR-0051: 構成案の生成を軽量ローカル LLM を主軸にする（Gemini は利用者が明示して選ぶ補助へ）

- **状態**: Accepted（方針・2026-09-30 利用者判断で入手と配布を確定＝下の「追補」）
- **日付**: 2026-09-30
- **Issue**: #1277（EPIC）
- **関連**: [`ADR-0010`](0010-real-ai-provider.md)（実 AI プロバイダ・APIキー・外部送信＝**本 ADR が一部を改める**）／[`ADR-0041`](0041-external-agent-operability.md)（同梱の生成と持ち込みの AI は別枠）／`CLAUDE.md §2-1`（AI は動画を作らない）・`§2-2`（AI 出力は検証してから）・`§2-6`（外部送信は事前確認）／[`12_AI_PROMPT_AND_MAPPING.md`](../12_AI_PROMPT_AND_MAPPING.md)／[`13_DEPENDENCIES_AND_LICENSING.md`](../13_DEPENDENCIES_AND_LICENSING.md)／提案書とレビュー [`2026-09-local-llm-proposal-review.md`](../archive/research/2026-09-local-llm-proposal-review.md)

## コンテキスト

構成案の生成は Gemini API の無料枠に依存しており、**混雑・レート制限・無料枠の枯渇・外部障害がそのまま生成の失敗として利用者に見える**（ADR-0010 の MVP 判断＝予算配慮で Gemini）。加えて、外へ出られない環境（社内ネットワーク・外部 AI を使えない契約）では構成案の生成そのものが使えない。

利用者判断（2026-09-30）：「Gemini 互換に依存する設計をかなり弱めて、**軽量ローカル LLM 運用を主軸にする方がよっぽど UX に良い**」。
外部の提案書（`star-recruit-studio_local-llm_design-proposal.md`・2026-09-25）を下敷きにし、現行の develop と突き合わせてレビューした（上記の research）。

## 決定

1. **既定の生成経路はローカル LLM**。Gemini（と将来の外部 AI）は**利用者が設定で明示して選ぶ補助**に下げる（ADR-0010 の「鍵があれば実プロバイダ、無ければ Mock」を改める）。
2. **既存の境界をそのまま使う**＝`AiProvider.generateVideoPlan()` の実装を1つ足す（`LocalVideoPlanProvider`）。プロンプトの組み立て（`buildVideoPlanMessages`）・受信後の検証（`parseAndValidateVideoPlan`＝ajv）・変換（`transformVideoPlan`）は**共有**。**正典の schema はローカルの都合で弱めない**（ローカル用の簡略 schema が要るなら別に作り、最後は正典で検証する）。
3. **実行はローカルの別プロセス**（llama.cpp の `llama-server` を第一候補）＝Rust が必要なときだけ起動し、**`127.0.0.1` だけで待ち受け**、しばらく使わなければ止める・アプリ終了で必ず止める。**CPU だけで実用になること**を最低条件にする（GPU・NPU は追加の高速化）。
4. ~~**モデルの入手は2つの道**~~ → **同梱に改めた**（下の「追補：利用者判断」決定9）。以下は当初の案（経緯として残す）：
   - **アプリの中から取得**＝大きさ・入手元を見せて**利用者が押してから**落とす（数百 MB〜1.3GB）。
   - **取り込み**＝別の機械で落としたファイルを選ぶ（外へ出られない環境の道）。
   - どちらも**入手元と SHA-256 を固定した一覧（manifest）で照合**し、合わないものは使わない。モデルとランタイムは**アプリ全体の持ち物**（プロジェクトには入れない＝ADR-0024 の自己完結の対象外・ADR-0038 のフォントと同じ扱い）。
5. **ローカルが失敗しても、黙って外部 AI へ送らない**（§2-6）。「もう一度ローカルで試す／外部 AI を使う（←既存の送信前確認を通る）」を出す。**Mock への自動の置き換えもしない**（生成に失敗したのに構成案が出たように見せない＝§2-5）。
6. **失敗は種類を分けて持ち、画面には次の行動を出す**（`15 §6` に足す）：モデルが無い／照合が合わない／起動できない／時間切れ／形が崩れた／正典の検証に通らない／意味の整合が取れない／メモリ不足／利用者がやめた。
7. **採用するモデルは実測で決める**（名前の印象で固定しない）。最低検証機＝Core Ultra 5 125U・RAM 16GB・Windows。評価は提案書 §12 の自動評価（schema 適合・存在しない ID・尺・文字数）と人手比較。**Gemini を正解扱いしない**。
8. **進め方は2段**：Phase A＝今のプロンプトのまま Local Provider を足して比べる（足りれば終わり）／Phase B＝足りなければ、テンプレ・素材の選択・尺の補正など**LLM にやらせなくてよい仕事をコードへ戻す**。

## 追補：利用者判断（2026-09-30）

利用者の判断（原文の趣旨）：「アプリでモデルをダウンロードするのではなく、**もとから同梱する**方針が良い（利用者ごとに一々ダウンロードさせない）」「入手元は **A＝公式の重みから自前で最適化・軽量化**し、さらに**このソフト専用に落とし込めたら最高**」「ローカル LLM 運用になることで、**ソフト内で AI を使える箇所を増やせる可能性**がある＝設計変更も視野として記録する」。

9. **モデルとランタイムは同梱する**（決定4 を改める）＝利用者の手元でのダウンロードは持たない。外へ出られない環境でも入れたその場で動く。
   - ⚠️ **配布物の大きさが未確認**（下の未決4）。取り込みの道（決定4）は**更新の手段**として残すかを、配布の形と合わせて決める。
10. **入手元は公式の重み（Qwen/Qwen3.5-2B・Apache-2.0）から自前で量子化する**（提案書 §6.1 の推奨どおり）＝第三者の GGUF は使わない。
    - 固定した llama.cpp の版で変換・量子化し、**手順と SHA-256 を記録して再現できるようにする**（開発の側で一度だけ落とす＝約 4.6GB）。
    - 公式の重みは画像も読む型（`image-text-to-text`）＝構成案には文字だけを使う（画像の入口は同梱しない）。
11. **このソフト専用に落とし込む（Phase C）を目標に置く**（提案書 §16 は「初期は行わない」＝**順番は守る**）：
    ① プロンプト・schema・コードの分担を詰める（Phase A/B）→ ② **教師データ**（入力 → 人が確かめた構成案）を溜める → ③ 追加学習（LoRA 等）で専用化 → ④ 量子化して同梱。
    専用化したものも**正典の検証を必ず通す**（決定2）。追加学習の成果物の由来（元の重み・データ・手順）を記録する。
12. **AI を使える箇所を増やす設計変更を視野に入れる**＝外へ送らず無料で何度でも使えるので、今は「構成案の一括生成」だけに絞っている AI を、編集の途中の小さな手伝いへ広げられる。
    候補（**採否は1つずつ決める**・どれも「提案を出し、利用者が選ぶ」＝勝手に書き換えない・AI は動画を作らない＝§2-1）：
    - セリフ・字幕の言い換え（短く・やわらかく・尺に合わせる）／読み上げの読み違いの指摘
    - 場面の見出し・動画の題名の候補
    - 場面ごとの見た目パターン・素材の候補（Phase B の「コードへ戻す」と分担を決める）
    - 公開前チェックの結果に「直し方の文」を添える
    - タイムライン形式での文字の部品の文案（⚠️ ADR-0032／ADR-0041 の「AI が触るのは場面形式まで」は**構成案の自動生成**の線引き。小さな手伝いをどこまで許すかは、広げるときに ADR で決める）
    ⚠️ 広げるたびに**検証してから内部へ**（§2-2）・**失敗は次の行動で返す**（§2-5）を守る。重い処理（書き出し・読み上げ）と同時に走らせる扱いも、そのときに決める（メモリ 16GB の最低検証機）。

## 未決（利用者判断が要る）

1. ~~入手元の採用~~ → **決着**（決定10＝公式の重みから自前で量子化）。ランタイムは llama.cpp の公式リリースを版を固定して同梱する。
2. ~~同梱か取得か~~ → **決着**（決定9＝同梱）。
3. **ライセンス告知**＝採用したモデル・ランタイムを `13` の台帳と About に載せる（Apache-2.0／MIT の想定・採用時に確認）。
4. **同梱したときの配布物の大きさ**＝MSI は VOICEVOX の同梱で既に約 2GB。モデル（2B の Q4 級で約 1.3GB）を足すと約 3.3GB。
   ⚠️ MSI の中の書庫（CAB）は1つあたり 2GB が上限＝以前 NSIS が大容量で使えなかったのと同じ種類の壁に当たりうる。
   **書庫を分ける／モデルだけ MSI の横に置いてインストーラが取り込む**などを、実際に作って確かめてから決める（0.8B なら約 0.5GB）。

## 採らなかった案

- **Gemini を主経路のまま、失敗時にローカルへ**：外部の混雑・無料枠が主経路の品質を決めるのは変わらず、外へ出られない環境で使えない。
- **ローカル失敗時に自動で外部 AI へ**：会社情報・素材の説明が無断で外へ出る（§2-6 違反）。
- **初手から Fine-tuning**：プロンプト・schema・コードの分担を先に詰める（提案書 §16 のとおり）。

## 実施の順（経路）

提案書 §14 を現行に合わせて並べ直したもの。Issue で追う。

（2026-09-30 の利用者判断で並べ直した＝同梱・自前量子化・専用化）

1. 現行（Gemini）の基準値を取る（成功率・時間・schema 失敗）。
2. **自前の量子化の手順を作る**＝公式の重み（約 4.6GB・開発の側で一度だけ落とす）→ 固定した llama.cpp の版で GGUF へ変換・量子化（2B／0.8B）→ SHA-256 と手順を記録（再現できること）。
   ✅ **2026-09-30 済み**＝`scripts/local-llm/build-model.sh`・記録は [`local-llm-build.md`](../local-llm-build.md)（再現を確認・最低検証機で**正典の schema をそのまま渡して検証に通った**・2B は約 19〜20 トークン/秒・メモリ最大 約 2.3GB）。
3. **同梱の形を実測で決める**（未決4）＝MSI に入るか・書庫を分けるか・横に置くか。manifest（同梱物の SHA-256・ライセンス）を作り、起動時に照合する。
4. ランタイムの起動・`127.0.0.1` 待ち受け・停止（Rust の別プロセス管理）。
5. `LocalVideoPlanProvider`（TS）＝既存の検証・変換に乗せる。生成の入口を「既定＝ローカル」へ・失敗時に Mock へ落とさない。
6. 最低検証機で 2B／0.8B を実測（Golden case 30〜50・自動評価＋人手比較）。
7. 足りなければ Phase B（仕事をコードへ戻す）。
8. **Phase C（専用化）**＝教師データを溜めて追加学習 → 量子化 → 同梱（決定11）。
9. **AI を使える箇所を広げる**（決定12）＝候補を1つずつ ADR で決めて足す。
10. 既定をローカルへ切り替え・ADR-0010 の該当箇所を Superseded に・`13` の台帳と About に告知。
