# ADR-0012: 画面比率の拡張と縦型動画（9:16 / 1080×1920）対応

- **状態**: Proposed（2026-06-18 起案）※スコープ（9:16のみ/＋1:1）とテンプレ作成範囲はユーザー確認待ち
- **日付**: 2026-06-18
- **関連**: `01_REQUIREMENTS §4.1-4.2,§16.2` / `02_MVP_ROADMAP §4` / `05_RENDERING_SPEC §4` / `CLAUDE.md §10` / `schemas/project.schema.json` / `schemas/template.schema.json` / `11_SCHEMA_REFERENCE` / `12_AI_PROMPT_AND_MAPPING` / `ADR-0001` / `ADR-0004` / `ADR-0006`
- **重要**: 本 ADR は **書き出しコーデック方式（案A/案C, `research/export-encoder-mediafoundation-vs-openh264.md`）とは独立**。縦型はコーデックの問題ではなく、データモデル＋テンプレ＋UI の横断対応である。

---

## コンテキスト

- ユーザーが **縦型動画（9:16・1080×1920）を必須要件**として扱うよう指定。
- 一方、**現行の正典は 16:9 固定**：
  - `schemas/project.schema.json` VideoSettings（55-60行）：`aspectRatio: enum ["16:9"]`、`width: const 1920`、`height: const 1080`、`fps: const 30`。
  - `schemas/template.schema.json`（17行）：`aspectRatio: enum ["16:9"]`（ただし `canvas.width/height` は可変＝23-24行）。
  - 縦型は **MVP除外／将来対応**：`01 §16.2`・`02 §4`・`CLAUDE.md §10`（「縦・正方形動画」）／将来対応＝`01 §4.2`・`05 §4`（9:16 1080×1920）。
- コーデックとの独立性（調査で確認済み）：
  - `renderer/export/buildExportScenes.ts` は PNG を `outputSize ?? template.canvas` の**実寸で焼くだけ＝寸法非依存**。縦キャンバスを与えれば縦PNGが出る（構造変更不要）。
  - `h264_mf`／OpenH264 いずれも**与えた実ピクセルを符号化**する（回転メタデータではない）。縦型可否はエンコーダに依らない。
  - `schemas/ai-video-plan.schema.json` に **向き/比率フィールドは無い**＝AI出力は向き非依存。向きは**プロジェクトのユーザー選択**であり、AIには影響しない。

→ よって縦型対応の本質は「**向き（orientation）を第一級の設定にし、向きに整合したテンプレを用意し、UI/マッピング/検証を向き対応にする**」こと。

## 判断軸

テンプレ駆動の維持（§2-4）／正典の単一参照（§2-7）／レンダラ非改修／既存16:9プロジェクトの互換（マイグレーション）／AI出力は向き非依存のまま／非技術者UX（向きは分かりやすい選択）。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| **(A) 向きを第一級概念化＋向き対応テンプレを用意** | テンプレ駆動を保ち構図が破綻しない。正典・型・UI・マッピングを向き対応に拡張。**採用（Proposed）** |
| (B) 16:9テンプレを回転して流用 | テンプレの座標前提が崩れ、ロゴ/字幕/人物配置が破綻。**不採用** |
| (C) 出力時に16:9を縦へクロップ/レターボックス | 構図破綻 or 上下黒帯で「縦型」の体をなさない。**不採用** |

## 決定（Proposed）

> **(A) を採用する。** `VideoSettings` に **向き（aspectRatio ∈ {`16:9`, `9:16`}）** を持たせ、`9:16` のとき解像度は **1080×1920**（実ピクセル）とする。テンプレは **向きごとに用意**し、AIマッピングは**プロジェクトの向きに整合したテンプレのみ**を選ぶ。レンダラ（SVG→PNG→FFmpeg, ADR-0001/0004/0006）は**寸法非依存のまま無改修**。`1:1` 正方形は将来の任意拡張として枠だけ残す。

## 結果・影響（実装計画：このADR承認後に着手）

> 本 ADR は計画。承認後に下記を小コミットで進める。**正典（schemas）変更は schemaVersion 更新＋マイグレーション同梱**。

1. **schemas（正典）**
   - `project.schema.json`：`aspectRatio` を `enum ["16:9","9:16"]` に拡張。`width/height` の `const` を**向きに整合する条件**へ（`if aspectRatio=16:9 then 1920×1080 / if 9:16 then 1080×1920` の `allOf/if-then`、または許可ペアの `oneOf`）。`schemaVersion` を上げ、既存=16:9 とみなすマイグレーションを `11.1` 方針で用意。
   - `template.schema.json`：`aspectRatio` を `enum ["16:9","9:16"]` に拡張（`canvas` は可変のまま）。
2. **domain 型／定数**
   - `domain/project/types.ts`：`VideoSettings.aspectRatio` を `'16:9' | '9:16'` に。必要なら `Orientation` 型を追加（§2-7：リテラル直書き禁止＝定数化）。
   - `domain/constants.ts`：向き別の寸法（`PORTRAIT_WIDTH=1080`/`PORTRAIT_HEIGHT=1920`）を追加。`WIDTH/HEIGHT` は横型既定として保持し、向きから寸法を導く関数/定数を用意。
3. **テンプレート（主な作業コスト）**
   - 縦型テンプレ（1080×1920）を**カテゴリ単位で新規作成**（opening/closing/photo_intro/point_list/message 等のうち、縦型で必要な範囲）。座標・レイヤーは縦型用に再設計。
4. **マッピング／AI（12）・検証**
   - `12_AI_PROMPT_AND_MAPPING`：テンプレ選択を**プロジェクトの向きで絞り込む**（向き不一致テンプレを選ばせない）。
   - `domain/ai/validateVideoPlan`／マッピング：解決後のテンプレ向きがプロジェクト向きと一致することを検証（不一致は自動補正＝同カテゴリの同向きテンプレへ）。
5. **UI**
   - 新規作成 or 書き出しで**向きの選択**（「横型(16:9)／縦型(9:16)」の分かりやすい表現）。`ExportScreen` のサイズ選択は向きに追従（縦型時は 1080×1920／必要なら軽量縦）。技術用語は出さない（§2-3）。
6. **レンダラ**
   - `buildExportScenes`／`layout`／`findVideoSlot`：寸法非依存を確認のうえ**原則無改修**（縦キャンバス・縦outputSizeで動くことをテストで担保）。
7. **テスト（14_TEST_STRATEGY）**
   - schema：16:9/9:16 の正常・異常（不整合ペア）データで ajv 検証。
   - golden-file：縦型テンプレの配置PNG期待値。
   - 単体：向き→寸法導出、マッピングの向き絞り込み、検証の不一致補正。
8. **ドキュメント整合**
   - `01 §16.2`／`02 §4`／`CLAUDE.md §10` の「縦型は除外」を、**ユーザー要件により対応へ昇格**する旨で改訂（理由付きで §9 の方針に従い更新）。`05_RENDERING_SPEC §4`・`11_SCHEMA_REFERENCE` を追従。

## 未解決の論点（ユーザー確認）

1. **対象の向き**：今回は **9:16 のみ**でよいか、**1:1 正方形**も同時に入れるか。
2. **縦型テンプレの作成範囲**：全カテゴリを縦型でも用意するか、主要カテゴリ（opening/message/point_list 等）に絞るか。
3. **既存16:9プロジェクトの扱い**：マイグレーションで全件 16:9 固定でよいか（破壊的変更の影響）。
4. **尺・上限**：縦型でも `VIDEO_HARD_MAX_SEC=600`／MVP想定尺を踏襲でよいか。
5. **コーデック方式との順序**：縦型トラックと h264_mf スパイクは独立並行で進めるが、リリースの優先度はどちらを先にするか。
