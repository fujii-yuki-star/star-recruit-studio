# ADR-0047: 編集画面の密度（操作の大きさと余白）

- **状態**: Accepted
- **日付**: 2026-09-25
- **関連**: [`ADR-0034`](0034-timeline-interaction-model.md)（操作は業界の型に合わせる）／[`ADR-0033`](0033-editor-panel-layout.md)（欄の配置は画面の好み）／`06_UI_SPEC.md §12.1`（#1104 の経緯）／`CLAUDE.md §2-3`

## コンテキスト

チュートリアル映像（#1228・ADR-0046）を撮るためにタイムライン編集を通しで操作したところ、
利用者から指摘が入った（2026-09-25）。

> 「一々太帯だったり、ボタンが大きかったりと実際に触るうえでは不便な部分が多いですよね。」
> 「実際に有名な動画エディターのスクショを持ってきましたが、**一画面にすべてしっかり収まっている**んですよね。」

**感想ではなく実測で押さえた**（タイムライン編集・1920×1057・明るい表示）。

| 測ったもの | 実測 |
|---|---|
| 画面に出ているボタン | **60個** |
| `.btn` 系の高さ | **ほぼ全部 41px**（primary 41 / secondary 41 / ghost 39〜41） |
| `.btn-sm`（小さいはずのもの） | **41〜43px**＝**小さくなっていない**（後述） |
| `.nav-item`（左の帯） | 42〜53px |
| 欄（`.card`）の内側の余白 | **24px**（`--gap-lg`）・例外なし |
| 列（`.timeline-lane`）の高さ | **28px** |
| 目盛りの行 | 22px |
| 画面に占める割合 | 置く **11%** / 仕上がり確認 **18%** / 選んだ部品 **9%** / 並び **38%** |

⚠️ **太いのは「帯」ではなかった**＝列は既に 28px まで詰めてある（#1104 で実機の指摘から決めた値）。
**太いのは操作と余白**で、そのせいで**本体（並び）が画面の 38% しか使えていない**（列が4〜5本しか見えない）。
最初の見立て（「行が 40〜50px ある」）は**総当たりの拾い方で別の行を数えていた**もので、測り直して訂正した。

### 決定的な事実：`btn-sm` は**存在しない**

`btn-sm` は**4ファイル・12か所**で使われているが、`src/styles/theme.css` に**規則が1つも無い**
（`grep -c "\.btn-sm" src/styles/theme.css` → **0**）。
つまり「ここは小さいボタンにしてある」と読めるコードが、**実際には普通の 41px のボタン**を出していた。
⚠️ **書いた人は小さくしたつもり**＝ドリフトではなく、**最初から効いていなかった**。
（同じ型を1日に3回踏んだ記録がある＝「門番の有無は書く前に grep する」）

### 正典の側の兆候

`06 §12.1` には #1104（2026-09-10）の利用者発言が残っている。

> 「タイムライン編集画面にスクロールをする必要が出てきてしまっています。これは絶対避けたいです」

このときの手当ては**この画面だけ下段を広げる**（0.28→0.5）という配置の調整で、
**操作の大きさには触れていない**。同じ原因（本体に割ける面積が足りない）に、2度目の指摘が来た。

また `ADR-0034` は「**操作は業界の型に合わせる／独自の操作を発明しない**」と決めているが、
**密度も型のうち**である点は言語化されていなかった。参考にした製品は、同じ縦幅に
**映像7列＋音2列＋波形**と2つのプレビューを収めている。こちらは列4〜5本で埋まる。

## 判断軸

1. **本体に面積を渡す**＝編集画面の主役は「並び」。周りの道具立てがそれを削ってはいけない。
2. **触る所を動かさない**＝押す物・置き場所・言葉は変えない（覚え直しを強いない）。
3. **業界の型**（ADR-0034）＝密度も型に含める。
4. **1か所で決める**（§2-7）＝大きさを画面ごとに書かない。`btn-sm` が効いていなかったのは、
   **寸法の正が無く、クラス名だけが約束していた**ため。
5. **押しにくくしない**＝ただし「見た目だけ小さく、当たり判定は大きいまま」は**見えない当たり判定**を生む
   （隣を押したつもりが別のものに当たる）。

## 検討した選択肢

| 選択肢 | 評価 |
|---|---|
| (A) 何もしない（配置でしのぐ） | ❌ #1104 で一度やった手で、同じ指摘が再発した。原因（操作の大きさ）に触れていない |
| (B) **編集画面に寸法の正を作り、まずタイムライン編集へ適用** | ⭕ **採用**。効果を実測で確かめてから他画面へ広げられる |
| (C) アプリ全体を一度に詰める | ❌ 困っていない画面（設定・一覧）まで動き、実機で見ていただく量が跳ね上がる |
| (D) 「ゆったり／ふつう／詰める」を設定に置く | ❌ 3通りすべてで崩れないことを検査で守る必要があり、いまの困りごとに対して高い |

**当たり判定**については2案あった。

| 案 | 評価 |
|---|---|
| 見た目だけ小さくし、当たり判定は今のまま | ❌ **見えない当たり判定**が隣と重なる。詰めるほど誤爆が増える |
| **見た目＝当たり判定で素直に小さくする** | ⭕ **採用**（利用者判断 2026-09-25）。押す物と場所は変えないので、当たりの形は今と相似 |

## 決定

1. **寸法の正を1か所に作る**（`--ctl-h` 等の寸法トークン）。クラス名だけで大きさを約束しない。
2. **まずタイムライン編集に適用**する。効果は**実測**（ボタン高・欄の余白・並びの面積・見える列数）で示す。
3. **見た目＝当たり判定**。素直に小さくする（利用者判断）。
4. **触る所は変えない**＝押す物・並び順・言葉・場所は据え置き。変えるのは**大きさと余白**だけ。
5. **`btn-sm` を実在させる**（12か所が意図どおりになる）。⚠️ **効いていなかったものが効き始める**ので、
   その12か所は**変化する側**として扱う（黙って小さくなる、を「直った」と混ぜない）。
6. **列（`timeline-lane` 28px）は触らない**＝#1104 で実機から決めた値で、今回の太さの原因ではない。

## 結果・影響

- `06_UI_SPEC.md §12.1` に密度の節を足す（#1104 の配置の手当てと**別の話**であることを明示）。
- `ADR-0034` の「業界の型」に**密度も含む**ことを、本 ADR から参照できるようにする。
- `schemas` / `11` は**変えない**（見た目の寸法は文書に入らない＝ADR-0033 と同じ流儀）。`schemaVersion` 据え置き。
- 検査：**クラス名だけの約束を作らない**ための門番（`src/app/**` で使っている `btn-*` / 寸法系クラスが
  CSS に実在すること）。⚠️ **今回の原因そのもの**なので、実装より先にこれを置く。
- 実測は**前後で同じ測り方**を使う（測り方を変えて「良くなった」と言わない）。

## 未解決の論点

- **他の編集画面へ広げるか**（場面編集・見た目パターン編集）＝タイムライン編集での効果を見てから（ユーザー確認）。
- **下限をどこに置くか**＝小さくしすぎると押しにくい。実機で触っていただいて決める（ユーザー確認）。
- **左の帯（`nav-item` 42〜53px）** は編集画面の外なので今回は触らない。畳めるので面積の問題は小さい。
