# ADR-0020: 取り消し/やり直し（Undo/Redo）モデル

- **状態**: Accepted（2026-06-26・α-3 ① #211・実装PRで実現）
- **日付**: 2026-06-26
- **関連**: [`adr/0016`](0016-detailed-editing-completion-roadmap.md)（詳細編集の完全化・**①の Undo/Redo は着手前にアーキ評価→必要なら独立ADR**＝未解決1）/ [`adr/0007`](0007-detailed-edit-mode.md)（詳細編集2モード）/ [`adr/0008`](0008-free-layout-editor.md)（FREE 自由配置）/ `src/app/store/projectStore.ts`（Zustand 単一ストア）/ `CLAUDE.md §4`（層分離）
- **対象**: α-3 ①の最後。FREE 詳細編集を中心に、文書編集の取り消し/やり直しを入れる。

---

## コンテキスト

α-3 ① でFREE編集（移動/リサイズ/整列/吸着/回転/体裁/重ね順/表示・ロック/コピペ/複数選択）を拡充した。**取り消し/やり直しが無いと「気軽に試す」ができず、利便性・直感性（プロジェクトのUX基準）を満たせない**。

ADR-0016 は「Undo/Redo は履歴/Command の設計（domain純粋性・状態管理への影響）が非自明ゆえ、着手前にアーキ評価し非自明なら独立ADR」と定めた。評価の結果、以下の非自明な判断があり本ADRを起こす。

### ストアの実態（評価で確認）
- Zustand 単一ストア。**Immer 不使用**、更新は `set((s) => …)`。
- **保存される文書**：`meta` / `parts` / `scenes` / `assets`。このうち **undo 対象は `meta` / `parts` / `scenes`**（`assets` は素材取込のディスクIOゆえ undo 対象外＝決定参照）。
- **transient（＝undo非対象）**：`status` / `saveStatus` / `*Error` / `isImporting` / `assetSrcById`（表示URL）/ `narrationAudioById`（音声）/ `templates` / `warnings`。
- FREE編集は `updateScene`（SceneEditScreen の `patch`）に集約。場面操作・テキスト等も同じ `set` 経路。

---

## 決定の判断軸

1. **正しさ・堅牢性**：戻す/やり直すで状態が壊れない。transient と文書を混ぜない。
2. **実装コスト・保守性**：操作が増えても破綻しない（§4 純粋性・最小の侵襲）。
3. **粒度の自然さ**：ドラッグ＝1ステップ。利用者の「1操作」と履歴の1件が一致。
4. **正典非汚染**：schema/永続データを変えない（履歴は保存しない）。

---

## 検討した選択肢

### 選択肢A: スナップショット方式（文書slice限定）【採用】
- **概要**：文書slice（`meta/parts/scenes`・**`assets` は除外＝下記**）を丸ごと履歴スタック（`past[]`/`future[]`）に積む。undo＝past を pop して復元・現在を future へ。
- 利点：**実装が単純で堅牢**（逆操作を定義しない）。操作が増えても履歴側は不変。transient を除けば壊れない。
- 欠点：1件＝文書全体のコピー。ただしプロジェクトJSONは小さく（KB〜）、深さ上限50でも数MB程度＝許容。

### 選択肢B: Command/逆操作方式
- **概要**：各操作に do/undo の対を実装。
- 利点：メモリ効率が良い。
- 欠点：**15+のストア操作＋多数のFREE純粋opすべてに逆関数が要り高コスト・脆い**（ADR-0016 が警告）。差分の取りこぼしで不整合に。**不採用**。

### 選択肢C: Immer パッチ方式
- 概要：Immer の produce でパッチ列を記録し逆適用。
- 欠点：**現状 Immer 不使用**。導入＋全 `set` の書き換えが必要で侵襲が大きい。**不採用**（将来メモリが問題化したら再検討）。

## 決定

> **スナップショット方式（選択肢A）で、文書slice（`meta/parts/scenes`・`assets` は除外）に限定した Undo/Redo を入れる。**

- **履歴slice**：`past: DocSnapshot[]` / `future: DocSnapshot[]` と `undo()` / `redo()` / `canUndo` / `canRedo` をストアに追加。`DocSnapshot = Pick<state, 'meta'|'parts'|'scenes'>`（**`assets` は含めない**＝素材の追加/削除を undo 対象外にするため・下記）。**深さ上限（既定50・定数）**を超えたら古い方から捨てる。
- **記録のしかた**：文書を変える操作は「適用前の文書」を `past` へ積み、`future` をクリアする。**transient のみの変更（status/error/フラグ/src/音声）は積まない**。
- **粒度・合成**：
  - 離散操作（追加/削除/整列/重ね順/トグル/数値入力の確定 等）＝1操作=1スナップショット。
  - **連続操作（ドラッグ移動/リサイズ・スライダー）は1ステップに合成**。FREE オーバーレイは drag 開始/終了が明確なので、**開始時に1回チェックポイント（pushHistory）→ 連続中は積まない → 終了**で確定する「コミット境界」方式。境界の制御は薄いAPI（`beginInteraction()`/`endInteraction()` 相当、または `pushHistory()` を操作の入口で呼ぶ）で実装する。
- **素材の取込/削除は undo 対象外（`assets` を snapshot に含めない理由）**：`addAsset`/`addAssetByPath`/`setAssetImage`/`setBgm`/`removeAsset` はディスクIO＋transient src を伴い、一覧から戻してもファイルは残る＝安全に戻せない。そこで **`assets` を `DocSnapshot` に含めず、素材操作は履歴に一切関与させない（push もクリアもしない）**。これにより：
  - (a) 編集の履歴は素材取込を**またいで保持**される（「素材を足したら Ctrl+Z が効かない」＝レビュー🟡 は起きない）。
  - (b) undo は assets を戻さない＝`scenes`/`parts` の `assetId` 参照は**切れない**（assets は取込で増えるだけ・undo で消えないので dangling にならない＝レビュー🔴 を解消）。
  - **素材の追加/削除そのものは取り消せない**点のみ、必要時にUIで一言（§2-5）。素材操作で履歴を消さないので「大量編集→素材追加で全部消える」混乱は起きない。
- **スコープ（グローバル）**：履歴は**ストアに置きプロジェクト内の画面遷移をまたいで保持**する。**別文書を開く操作（`newProject`/`loadProject`）で履歴をクリア**（`saveProject` ではクリアしない）。場面横断の編集（並べ替え・分割等）も同じ履歴に乗る。
- **入口**：Ctrl+Z＝undo / Ctrl+Y・Ctrl+Shift+Z＝redo（**App 一箇所で登録**＝画面ごとの二重登録〔二重 Undo〕を防ぐ・#413。IME変換中やテキスト入力中の既定動作は奪わない）。**有効にする画面は「取り消す/やり直す」ボタンを置く画面＝たたき台・場面編集・タイムライン編集**のみ（`UNDO_REDO_SCREENS`）。「取り消す/やり直す」ボタンも同じ3画面に置く（`canUndo/canRedo` で活性制御）＝**ボタンとキーボードの入口を一致**させる（ADR-0026②）。
  - **掴んでいる間は効かせない（#686・#830）**＝掴んだ足元で文書が戻ると、離したときに**掴んだときと違う結果**に
    なる（起点だけ古い）。判定は**掴んでいる数**1か所（`isPointerDragging`）で見る
    ＝ただし**見ているのはキー入口**（`useUndoRedoShortcuts`）で、**ボタンは見ていない**（同じ指でスライダーを
    握ったままボタンは押せないので到達しない。2本目の指で押す経路だけが理屈の上で残る＝そこは未対応）。⚠️ **スライダーも数に入れる**
    （#830）＝`<input type="range">` は**入力欄扱いでも掴んでいる扱いでもない**ので、入れないと掴んだままキーが通り、
    `undo` が開いているまとめを畳んで（#817）**残りのドラッグが毎tick 1履歴**になり、上限（50）を**1回のドラッグで
    流し切る**＝取り消しでしか戻せない編集（場面の削除・種類の切替）を押し出す。入れるのは**まとめを開く側**
    （`useHistoryGroup` の `dragGroup`）＝両形式が同じ関数を通るので、片方だけ塞がることがない（ADR-0026②）。
  - **#413 の「全画面登録＝素材管理など編集画面以外でも効く」は #547 P1-1 で一部 Superseded**（2026-07-16）。理由＝**編集を画面ローカル state で持つ画面**（テンプレ作成＝`LooksEditScreen` の `draft`）で Ctrl+Z を有効にすると、**画面外の場面/メタ編集を無言で巻き戻し**、`undo` が立てる `saveStatus:"idle"` を見た自動保存が**その巻き戻しを永続化**してしまう（データ喪失・ADR-0026④）。履歴を画面で扱っていない画面（素材管理等）でも「見えていないものを Undo する」ことになるため同様に外す。**#413 の意図（たたき台の削除/移動も Ctrl+Z で戻せる）は `draft` を含めることで維持**。
  - 除外画面にも履歴 slice を触る操作はある（声/BGM/ウィザード入力＝`updateVoiceSettings`/`setBundledBgm`/`applyProjectInfo` は pushHistory する）が、**その画面に取り消す/やり直すUIが無い**＝Undo の結果を確認できないため対象外とする（多くはテキスト入力＝入力欄ガードで元々効かない）。
  - **これは「入口の集約」であって能力の喪失ではない**：履歴は**グローバル**（上記「スコープ」＝プロジェクト内の画面遷移をまたいで保持）なので、除外画面で積まれた履歴（例：仕上がり確認の「BGMを入れる」トグル＝`Switch` は `role="switch"` の button ゆえ入力欄ガードに当たらず従来は Ctrl+Z で戻せた）も、**たたき台/場面編集/タイムライン編集へ移れば「取り消す」または Ctrl+Z で戻せる**。失われるのは「その画面で即 Ctrl+Z できること」だけで、データ喪失リスクの除去に対し十分小さい（#547 P1-1 レビュー合意）。**書き出し中は undo/redo とも no-op**＝進行中の書き出しが不整合な `scenes/parts/meta` を読むのを防ぐ（`newProject`/`loadProject` と同じ #379 ガード）。
  - **保存前の「画面ローカル下書き」は局所履歴で扱う（#547 P2-3・2026-07-22 追記）**：テンプレ作成（`LooksEditScreen`）は編集を store でなく画面ローカルの `Template` draft に持つ。上記のとおり store Undo の対象にはできないが、復旧手段が「破棄して戻る」しか無いのは①の編集UXとして不足（1回の誤ドラッグで全編集の破棄を迫る）。そこで**下書き専用の局所履歴**（`useDraftHistory`）を与える。
    - **判定基準の言い換え**：`UNDO_REDO_SCREENS` は「取り消すUIがある画面」ではなく **「store 履歴（`meta`/`parts`/`scenes`）をその画面で編集している画面」**。取り消す/やり直すUI を持つ画面は4つ（＋テンプレ作成）だが、**store 履歴の入口は従来どおり3画面**で不変。
    - **履歴の“系統”は増やさない**：局所履歴が扱うのは**文書 slice の外にある保存前の下書き**だけ（保存すると通常の `templates` 更新＝従来どおり）。純粋関数（`domain/project/history.ts`）とグループ規約（遅延記録・1ドラッグ=1ステップ）は store と**共有**し、意味論を二重実装しない。
    - **[ADR-0028](0028-per-use-clip-and-undo.md) の「(C) 専用の別 Undo スタック＝却下」とは別件**：あちらが却下したのは**文書データ（クリップ調整）に対する第2の履歴**（同じ対象を2系統が奪い合い Ctrl+Z の一貫性を失う）。ここは**文書ではない保存前の下書き**が対象で、対象が重ならないため一貫性は損なわれない。
    - **書き出し中ガードは不要**：上記「書き出し中は undo/redo とも no-op」は**文書 slice を守る**ためのもの。局所下書きは書き出しのスナップショットに入らず MP4 に影響しないので、書き出し中も編集・取り消しできる（止めているのは保存/削除のみ＝#570）。
- **保存状態**：undo/redo は `saveStatus: "idle"`（未保存）にする。
- **正典影響なし**：履歴は永続化しない。schemaVersion 不変。

## 結果・影響

- **新規**：ストアに history slice（`past/future/undo/redo/canUndo/canRedo` ＋ `pushHistory`/コミット境界）。`DocSnapshot` 型。深さ上限定数（§2-7：定数モジュール）。
- **既存の侵襲は最小**：文書を変える `set` の前で `pushHistory` を呼ぶ（または set をラップする薄いミドルウェア）。連続操作は SceneEditScreen/オーバーレイの drag 境界でコミット。
- **テスト（§7）**：履歴の純粋ロジック（push/undo/redo/上限/future クリア/transient 除外）を中心に。スナップショット採用ゆえ復元は値の差し替えで検証容易。
- **層分離（§4）**：履歴の純粋部分（スタック操作・スナップショット差し替え）は domain 寄りの純粋関数に切り出し、ストアは薄く繋ぐ。
- **将来**：メモリが問題化したら Command/Immer へ移行可（履歴slice の内部実装差し替えで外部APIは不変に保つ）。タイムライン/キーフレーム（③④）導入時に履歴の粒度方針を再確認。

> **解決済み（レビュー反映・2026-06-26）**：旧・未解決3（素材取込の扱い）と旧・未解決5（スコープ）は決定へ格上げ＝**`assets` を snapshot に含めず素材操作は履歴に非関与**（🔴 の矛盾解消・🟡 の「履歴消失」回避）／**グローバル履歴（`newProject`/`loadProject` でクリア）**。

## 未解決の論点

1. **コミット境界の実装**：`pushHistory()` を各操作入口で明示呼びするか、`set` ラッパ＋ドラッグ中フラグで自動化するか（前者は明示的で安全・後者は侵襲小だが取りこぼし注意）。実装PRで確定。
2. **連続操作の合成範囲**：ドラッグ以外（スライダー・連続キー入力）をどこまで1ステップにまとめるか（同種連続をXms窓で合成する案も）。
3. **深さ上限の値**：既定50で足りるか。メモリ実測で調整。
