# ADR-0001: プレビューと本番出力の一致方式（描画アーキテクチャ）

- **状態**: Accepted（2026-06-10 承認）
- **日付**: 2026-06-10
- **関連**: `05_RENDERING_SPEC.md` / レビュー論点③（最大の技術リスク） / `CLAUDE.md §11`
- **将来**: 場面内アニメは [`adr/0019`](0019-keyframe-animation-model.md)（Proposed・④）が**選択肢C（毎フレーム描画・下記 §選択肢C）を発火**し、本ADRの「**場面内静止**」前提を将来 supersede 予定（A2ハイブリッド・パリティ原則・共有ロジックは存続。アニメ無し場面は静止1枚のまま）。

## コンテキスト

`05_RENDERING_SPEC.md §2` は「プレビューと本番MP4出力はできるだけ見た目を一致させる」を要件としている。しかし現状は **プレビュー＝DOM/Canvas（アプリ内）／本番＝FFmpeg（MP4）** という**2つの異なる描画エンジン**を使う前提で、両者の一致方法が未定義。

主利用者は非技術者で、**「プレビューで見た目を確認し、それがそのまま完成品になる」という信頼**が製品価値の根幹。ここがズレると「プレビューと違う動画が出力される」となり致命的。特に難しいのは:

- **日本語テキスト**の自動折返し・行間・字詰め・字幕の改行位置
- **フォント**のレンダリング差（ヒンティング・アンチエイリアス）
- **半透明・角丸パネル**、装飾、zIndex合成

これは事前レビューで**最大の技術リスク**と位置づけた。`renderer/preview` と `renderer/export` の設計全体を規定するため、実装前に方式を確定する。

### MVPの前提（重要）

- 16:9 / 1920×1080 / 30fps。
- **シーン内のレイアウトは静止**（MVPではKen Burns・キーフレーム・口パク等の動きなし）。動くのは **動画スロットの中身** と **音声** のみ。
- シーン間トランジションは `none` / `fade` / `slide`（**ADR-0009 で slide を MVP に追加**。書き出しは xfade 連結。場面"内"が静止である点は不変）。
- テンプレはレイヤー＋zIndexモデル（`04` / `11 §5`）。

この「シーン内は基本静止」という性質が、方式選択を大きく左右する。

---

## 決定の判断軸

1. **パリティ最優先**：プレビュー＝完成品の一致（特に日本語テキスト）。
2. **日本語・装飾の描画品質**。
3. **実装/保守の容易さ**、グラボ無し業務PCでの速度（`01 §15.2`）。
4. **既存のレイヤー/zIndexモデルとの相性**。
5. **将来拡張**（縦動画・簡易アニメ）への余地。

## 検討した選択肢

### 選択肢A: Web描画を「正」とし、静止レイヤーをラスタライズ → FFmpegは合成・音声・尺・結合に限定

プレビューに使うのと**同一のHTML/CSS描画**でシーンの静止レイヤーを画像化し、FFmpegは「動画スロットの合成・トランジション・音声ミックス・尺・エンコード」だけを担う。

**A2（ハイブリッド・推奨形）**: 静止レイヤーを**動画スロットより下／上の2枚の透過PNG**に分割して書き出す。
- 動画**なし**シーン: 全レイヤーを1枚のPNGに焼き、FFmpegは `durationSec` だけ静止表示。→ プレビューと**完全一致**。
- 動画**あり**シーン: `下PNG（背景等 zIndex<動画）` → `動画スロット（FFmpegでスケール・配置）` → `上PNG（パネル/文字/ゆうこ/字幕 zIndex>動画）` を `overlay` で重ねる。

- **利点**
  - パリティを**構造的に保証**（レイアウト・文字を描くのは常に同じWebエンジン）。
  - 日本語折返し・フォント・半透明角丸パネルはブラウザが正確に処理（CSSの表現力）。
  - FFmpegを**得意領域（動画・音声・尺・エンコード）に限定**でき、FFmpegグラフが単純。
  - 既存レイヤー/zIndexモデルと自然に対応。
- **欠点**
  - 静止レイヤーを**オフスクリーンでPNG化する経路**が必要（Tauri WebView / Canvas / 既製ライブラリ）。← 唯一の未知数。
  - 動画ありシーンは「下/上」2枚に分割するロジックが要る（zIndexで機械的に分割可能）。

### 選択肢B: FFmpeg `filter_complex` で全要素を構築

`drawtext` / `overlay` / 図形描画でテキスト・パネル・ゆうこ・字幕まで全部FFmpegで組む。

- **利点**: ブラウザ非依存・高速・決定論的。中間PNGが不要。
- **欠点**
  - **日本語 `drawtext` が困難**：自動折返しが無く改行を自前計算、フォント指定が煩雑、縦位置・字間調整が手作業。
  - プレビュー（ブラウザ）と**同じ折返し・座標を再現するのが極めて困難** → パリティ要件と正面衝突（=本プロジェクト最大のリスクを抱え込む）。
  - 半透明角丸パネル等は結局PNGを用意して重ねることになり、Aの利点を取りこぼす。
  - 実質「レイアウトエンジンをFFmpegフィルタで再実装」になり、保守コスト大。

### 選択肢C（将来オプション）: 毎フレームをWeb描画してフレーム列→動画

シーン内に動き（Ken Burns等）を入れたくなった段階で、静止1枚でなく**毎フレームをラスタライズ**してフレーム列から動画化する。MVPでは過剰・低速だが、Aの自然な拡張として将来取りうる。

## 決定

> **選択肢A（A2ハイブリッド）を採用する（Accepted, 2026-06-10）。** すなわち、**静止レイヤーはプレビューと同一のWeb描画でPNG化し、FFmpegは動画スロット合成・トランジション・音声ミックス・尺・結合・エンコードに限定する。**

理由：本製品の生命線である**パリティを構造的に保証**でき、最難関の日本語テキスト描画をブラウザに任せられる。Bはパリティ要件に対してリスクが最大で、本プロジェクトの一番の懸念をそのまま技術的負債にする。Cはシーン内アニメが必要になった将来にAから段階移行できる。

唯一の未知数である「オフスクリーンPNG化の具体手段」は **Phase 0 の技術検証**（`02_MVP_ROADMAP.md` Phase 0）で小さく実証してから本実装に入る。

## 結果・影響

- **共有の配置解決ロジック**：`domain` に「シーン＋テンプレ → 各レイヤーの矩形・テキスト・zIndex・スタイル」を解決する純粋ロジックを置き、`renderer/preview` と `renderer/export` の双方が使う。テキストの実描画（折返し・計測）はWebエンジンに委ねるため、preview と export で**同一フォント・同一CSS**を使うことを必須とする。
- **エクスポート経路**：シーンごとに静止レイヤーを透過PNG化（動画ありは下/上2枚）→ FFmpegでシーン単位の一時MP4を生成（`05 §6`）→ `xfade`(fade)等で結合 → 音声ミックス（ナレーション/BGM/動画元音声、音量は `11 §4,§6`）→ 最終MP4。
- **FFmpegの責務**：動画スケール/配置・`overlay`・`xfade`・`amix`・尺・H.264/AAC エンコードのみ。テキスト描画はしない。
- **フォント**：同梱日本語フォントを preview/export で同一指定（埋め込みライセンスは ADR-0002 / Tier2-E で確認）。
- **05_RENDERING_SPEC.md** はこの決定に追従して改訂する（承認後）。
- 中間PNGは `renders/preview` / `renders/export` 配下で管理し、クリーンアップ対象（`05 §19`）。

### FFmpeg合成イメージ（参考・確定仕様ではない）

```text
# 動画なしシーン: 1枚のPNGを尺ぶん保持
-loop 1 -t {dur} -i scene_full.png  → [encode]

# 動画ありシーン: 下PNG + 動画 + 上PNG
[below.png][video(scaled,xy)] overlay → [tmp]
[tmp][above.png]              overlay → [scene]
# シーン間: xfade=transition=fade
# 音声: [narration][bgm(vol,loop,fade)][orig(vol)] amix
```

## 未解決の論点（Phase 0で検証）

1. **オフスクリーンPNG化の手段**：Tauri WebView のヘッドレス描画 / `<canvas>`へのレイヤー描画 / `html-to-image` 系ライブラリ / OS印刷API のいずれが安定・高速か。← Aの実現性の肝。
2. **テキスト計測の一致**：preview と PNG化経路が同一レンダラ・同一フォントなら一致するはずだが、フォントのロード完了待ち等の落とし穴を検証。
3. **動画スロットの色・ガンマ**：PNG overlay と動画の色空間差。
4. パフォーマンス：5分・最大80シーンでのPNG化＋FFmpeg所要時間（グラボ無しPC）。

> Phase 0 の完了条件（`02`）に「静止PNG＋動画スロット＋字幕＋音声で数秒のMP4を生成し、同シーンのプレビューと一致する」を追加することを推奨。

## スパイク結果（2026-06-11）

`scripts/adr0001-spike.ts`（実行: `npx tsx scripts/adr0001-spike.ts`、出力は `.spike/`）で、方式A2の核を実証した。

**実装した共有コード（本実装）**
- `src/renderer/layout.ts`：`layoutScene(scene, template)` ＝ レイヤーの矩形・zIndex・内容・スタイルを**決定論的に**解決（preview/export 共有）。
- `src/renderer/sceneSvg.ts`：`layoutToSvg(layout)` ＝ レイアウトを **SVG文字列**へ。
- 単体テスト 3件（決定論性＝同入力で同SVG を含む）。`npm test` 全green。

**検証できたこと**
- **描画中間表現に SVG を採用**：プレビューは WebView でSVGを表示、出力は**同一SVG**をラスタライズ。
- Mock(ai-video-plan) → 変換 → レイアウト → SVG → **PNG**（`@resvg/resvg-js` ＋ Noto Sans JP）で 2シーン（opening / photo_intro）を 1920×1080 生成。**日本語は正しく描画**（tofuなし。スクショ確認済み。タイトル/本文/字幕帯/半透明パネル/ゆうこ/ロゴの配置も意図どおり）。
- **パリティの核**：同一SVGを同一ラスタライザで2回描画 → **byte-identical**。すなわち *preview と export が同じSVG＋同じラスタライザを使えば一致は構造的に保証される*。

**FFmpeg**：本環境に未導入のためコマンド確定のみ（`-c:v libopenh264`）。バイナリ導入後（`ADR-0002`）に「静止PNG→MP4」「下PNG＋動画＋上PNG overlay」を実機確認する。

**結論**：方式A2は実現可能。最大リスク（日本語テキストのパリティ）は解消方向。
