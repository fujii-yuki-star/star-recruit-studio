# ローカル LLM 化の提案書を、現行の develop と突き合わせたレビュー

- 対象：利用者から受け取った `star-recruit-studio_local-llm_design-proposal.md`（2026-09-25・外部の設計提案。**実装指示ではない**と本文に明記）
- 突き合わせた基準：develop（2026-09-30・#1276 まで）
- 決定は [`ADR-0051`](../../adr/0051-local-llm-primary.md)・EPIC #1277。本書は**根拠と、次の作業者が迷わないための地図**。

## 提案の要旨

構成案の生成を Gemini API から**ローカル LLM（llama.cpp の `llama-server`＋GGUF の小型モデル）**へ移す。
既存の `AiProvider` 境界に `LocalVideoPlanProvider` を足し、プロンプト・検証・変換は共有。Phase A（今の契約のまま比較）→ 足りなければ Phase B（LLM の仕事をコードへ戻す）。
ローカル失敗時に外部へ自動で送らない。モデルは実測で選ぶ（候補＝Qwen3.5 2B・0.8B・日本語特化 1.2B〔ライセンス要確認〕）。

## 提案書に足した・改めた点

1. **取得だけでなく「取り込み」も最初から入れる**＝外へ出られない環境（利用者の主な動機）で、別の機械で落としたファイルを選べる。どちらも同じ manifest で照合する。
2. **Mock へ自動で落とさない**を、提案書の「推奨しない」から**決定**に上げた（今の実装は鍵が無いと Mock＝構成案が出たように見える）。
3. **モデルとランタイムはアプリ全体の持ち物**＝プロジェクトに入れない（ADR-0024 の対象外・ADR-0038 のフォントと同じ筋）。
4. **入手元の採用は利用者判断**＝アプリが外部の実行物とモデルを落として動かすことになる。2026-09-30 に入手元の一覧を作ろうとして作業の安全装置に止められた（外部の実行物の取り込み）ので、**判断を先に取る**。
   - 調べて分かったこと（入手元の具体は判断の後に manifest へ入れる）：
     - 提案書の候補の**公式の重み**（Apache-2.0）は実在する。
     - 公式の配布元に **GGUF（量子化済み）は無く**、第三者の量子化が複数ある。
       → 「公式の重みから自前で量子化して固定する」か「第三者の GGUF を SHA-256 で固定する」かを選ぶ必要がある（提案書 §6.1 は前者を推奨）。
     - llama.cpp は公式リリースに Windows の CPU 版・Vulkan 版の配布物（ZIP・数十 MB）があり、GitHub の配布物に SHA-256 が付いている。
